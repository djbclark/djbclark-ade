**Update, 2026-10-14 (later).** First a correction: after filing I found **#819**, which reports the same root cause (the guest TSI `accept()` holds `lock_sock` across the blocking vsock round trip, so `getsockname()` blocks). This issue is a near-duplicate; I keep it open only as the wider list of calls the lock affects, and I am fine with it being closed in favour of #819. (My earlier search used "shutdown accept" and similar and missed it.)

New measurements (runner libkrun "2.0-sipb", guest kernel 6.12.91; control: the same programs on Ubuntu 24.04, Linux 6.18.15):

1. **A blocking `recv()`/`read()` holds the lock too, and what it blocks includes `send()`.** [`duplex-probe.c`](https://github.com/djbclark/djbclark-ade/blob/236ba60/skills/forgejo/examples/plektra/duplex-probe.c): one thread is parked in `recv()` on a connected socket (tested on the client end and on the accepted end), a second thread `send()`s on the same socket. Nothing reaches the peer until the parked `recv()` is released (the probe releases it after 3 s; `send()` then returns after 3004 ms). Normal kernel: 0 to 1 ms. Any client with a reader thread and a writer thread stalls: okhttp's WebSocket client was the case that found it (three tests in a 1,417-test suite timed out deterministically).
2. **A thread parked in `poll()` does not hold the lock.** With the reader parked in `poll(-1)`, in `poll` with a 20 ms timeout, or in a non-blocking `recv` loop, `send()` reaches the peer in 0 to 1 ms (same probe, `reader=poll|pollslice|nonblock`). So waiting in `poll()` before a blocking `read`/`accept` avoids all of it from userspace; the LD_PRELOAD shim [`loopback-port-shim.c`](https://github.com/djbclark/djbclark-ade/blob/236ba60/skills/forgejo/examples/plektra/loopback-port-shim.c) now does exactly that (`read`, `recv`, `recvfrom`, `recvmsg`, `accept`, `accept4`; signals still interrupt the `poll`, so the JDK's close wake-up still works).
3. **Result.** The full Plektra Gradle/Robolectric suite (1,417 tests) on the runner: 7 failures per run (one known unrelated test plus about six flaky MockWebServer/WebSocket tests, a different subset each time) before the shim changes; **1 failure** (a test that also fails on GitHub Actions and on a laptop) in two consecutive runs after (runs 229 and 230). A standalone okhttp 4.11 `MockWebServer` + WebSocket echo loop went from 0 of 60 echoes to 60 of 60, and 800 HTTP round trips from 150 s to 1 s.
4. The "second TSI loopback issue" I mentioned in the description was partly my own shim (it gave consecutive listeners the same random port within one second) and partly a separate libkrun behaviour, filed as #929.

Question: could the guest TSI driver wait for the vsock reply without holding the socket lock, the way `tcp_recvmsg` waits with `sk_wait_data` (which drops the lock while sleeping)? I have not tried a kernel patch.
