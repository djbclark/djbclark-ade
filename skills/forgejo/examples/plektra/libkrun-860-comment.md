A single-guest consequence of the always-on `SO_REUSEPORT`, in case it helps: inside one TSI guest, with `SO_REUSEADDR` set on both sockets (the JDK default for `ServerSocket`), a second `bind()`+`listen()` on a port that already has a listener in the same guest succeeds, in the same process and from a second process. A normal Linux kernel fails both with `EADDRINUSE` (Ubuntu 24.04, Linux 6.18.15; runner: libkrun "2.0-sipb", guest kernel 6.12.91). Without `SO_REUSEADDR` on the second socket it does fail as expected. [`dup-bind-probe.py`](https://github.com/djbclark/djbclark-ade/blob/236ba60/skills/forgejo/examples/plektra/dup-bind-probe.py) prints the whole matrix. Connections to the port then go to either listener, which breaks callers that rely on `EADDRINUSE` to pick a free port.

Also relevant to shared CI hosts, as an inference from your report and not something I tested: since the proxy socket lives in the host's network namespace, two concurrent jobs that each run in their own VM and pick the same port would both get a successful `listen()`. A related problem, listeners that outlive a `close()` during a blocked `accept()`: #929.
