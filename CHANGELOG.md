# Changelog

All notable changes to this repository are recorded here, newest first, in the
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/) form. Every pull request adds its line
under **Unreleased** (AGENTS.md, code review rule 10, since 2026-10-20); a tag moves that section
under a dated heading. `ade update` (proposal 4.4 item 9) prints the entries between the commit a
machine last applied and the head it is moving to, so this file is what tells an operator or an
agent what changed and what is new. Entries end with the pull request number.

- `bin/pr-wait` reads the **adversary verdict from a machine-readable marker** in the PR body, because the house rule that a teammate's PR carries an adversary verdict and the head it reviewed had no enforcement (PR 61 merged with no quote and nothing noticed): `<!-- adversary-verdict:v1 {"verdict":"APPROVE"|"BLOCK","head":"<40-hex>"} -->`. The `:v1` suffix is part of the match, the way AGENTS.md rule 9 reads Codex's `codex-review-state:v1`. A missing or unknown `verdict` fails closed; `head` must be 40 hex **and** equal the PR head (another head is not a pass); a malformed marker is its own outcome so a typo reads as a typo; and the rule is **asymmetric**: an APPROVE must be live, while a BLOCK naming this head — full 40-hex, or a 7+ hex prefix of it with or without a trailing `…`/`...` — is read from the **raw body**, so no code fence or strip bug can hide it (adversary review of 4a56c01, B1; the raw-body rescue used to be full-sha only, and four ordinary Markdown shapes made `_strip_code` over-strip and hide a shortened-sha BLOCK). The summary gains `adversary` (whose own keys include `conflict`), `adversary_warnings` and `adversary_required`. It **reports by default and blocks only when opted in** (`--adversary-required`, or an `adversary-required` label), because `merge_ready = not blockers` and a global default would block every PR in the house. **Prose verdicts are deliberately NOT read** — the first version parsed English and **two** adversary rounds found false approvals and false misses, including a BLOCK silently deleted by a prose filter, so the parser was deleted rather than patched (a third round reviewed this marker design and found the shortened-sha hole above). **A malformed marker is never OK**, even beside a valid APPROVE, and it blocks as `adversary-malformed`; a duplicate JSON key, an odd-cased verdict, a near-miss spelling (`adversary-verdict`, `adversary_verdict`, a dropped `:`) and an unclosed `<!--` all count as malformed, and the detail names which mistake it was. **70 new test functions** (77 → 147 in the file; all 165 collected tests pass), including gate-level tests through `assess()` and end-to-end runs of `main()` against a fake `gh` (none of the new ones are parametrized). Fenced blocks and inline code spans are stripped before matching, CommonMark-faithfully (a fence opens only at indent ≤ 3, remembers its character and length, and closes only on the same character at ≥ that length; spans do not cross a line), and only an APPROVE may be skipped as documentation — the template's placeholder head (`<40-hex>`), never a BLOCK. The bundled re-review of 66/67 then closed five shapes in the raw-body/strip interaction, each pinned by its own test: the marker's BOUNDARY is JSON-aware (an unclosed start quoted in prose ran to the next `-->`, swallowed the BLOCK that followed and read as a live APPROVE; a tempered regex fixed that and then hid a BLOCK whose JSON `note` quoted `<!--`, so the boundary is now a string- and escape-aware scanner shared by the live path and the rescue, which also reads a marker the format itself quoted inside another marker's `note` as content rather than a second typo, with the tempered capture kept only as the fallback for JSON that does not balance), code spans are CommonMark's equal-length backtick runs (a double-backtick span holding one backtick is code, not a live marker), stripping only ever replaces characters with spaces and never deletes (so a typo cannot be "repaired" into different JSON) and never changes the length (so a marker whose JSON slice differs between the raw body and the stripped text is `malformed` rather than read as an APPROVE), a backtick in a backtick fence's info string makes it inline code and not a fence, a full 40-hex sha with a trailing `…`/`...` is a BLOCK and not a malformed head, a raw-body BLOCK now reports `malformed` from the live validation so the rescue cannot launder a typo beside it, and the rescue scans EVERY marker start rather than resuming after one it has accepted (a candidate was accepted on balanced braces before its JSON was validated, so a real same-head BLOCK nested inside a rejected outer candidate was skipped and the body read as a clean APPROVE — the two shapes the re-review of `eb90d20` found). Known limits (accepted): a mistyped BLOCK quoted inside code, whose head is not a prefix of this head, is documentation — the raw-body rescue only recognises a head that actually names this head; and three code shapes outside "fences and inline spans" still read as live markers (an inline span broken across a line, a 4-space indented code block, a fenced block inside a blockquote), which can only add an APPROVE, never hide a BLOCK (#66).
