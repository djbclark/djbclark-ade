## 1. `paseo send` (E3): CHANGES E3

- Flags (`packages/cli/src/commands/agent/send.ts`): `<id>` (prefix ok), `[prompt]` | `--prompt <text>` | `--prompt-file <path>` (exactly one), `--image <path>` (repeatable), `--behavior interrupt|steer`, `--no-wait`, `--json`. **No `queue` behaviour.** Default: steer when `PASEO_AGENT_ID` is set, else interrupt; if steer is unavailable the running turn is interrupted and replaced.
- Without `--no-wait` it blocks until the turn finishes (`waitForFinish`, hard-coded 600000 ms); result `status` ∈ {queued, sent, completed, timeout, permission, error}. With `--no-wait`, `status` is the daemon receipt's `deliveryStatus`: `queued` ("Message queued for delivery after two quiet seconds") or `sent`.
- **Exit status pitfall**: exit 1 only on a thrown error (no daemon, unknown agent, bad prompt, `SEND_FAILED`). `completed`, `timeout`, `permission`, `error` and `queued` all exit 0. **The E3 shim must parse `--json` and read `.status`, never `$?`.** Standing order 10's rewrite ("a message is sent with `paseo send` and its exit status read") is wrong as drafted: it reads `.status ∈ {sent, completed}` as delivered; `queued` is not proof.
- `paseo wait <id> [--timeout S] [--json]` (`wait.ts`) blocks until idle; status idle | timeout | permission | error; a timeout also exits 0. Mapping: relay `--wait S` → `paseo send --no-wait --json` then `paseo wait ID --timeout S --json`. relay `--ack` has no native equivalent: a named ack still needs a reply through `paseo send` from the peer.
- Self-address: `PASEO_AGENT_ID` and `PASEO_WORKSPACE_ID` are documented as set "when a Paseo agent runs a CLI command"; not verified that a Claude session's Bash inherits both: probe in the first Wave 3 session. The daemon receives `sourceAgentId`, so a receiver can see the sender.

The parent is the label `paseo.parent-agent-id` (`paseo ls --label k=v` filters). No pid anywhere in the agent snapshot.
- Consequence: load-watch's find-and-tell cannot attribute a CPU spike from `paseo ls` alone. E5's brief picks one and tests it.

## Correction to item 1 (E3 adversary review, 2026-11-06, read from getpaseo/paseo @ 9f68af0)

A `paseo send` made with `$PASEO_AGENT_ID` set carries `sourceAgentId` (`send.ts:201-218`), and the daemon queues every such send into the recipient's 2-second batch and reports `deliveryStatus: "queued"` before dispatch (`session.ts:8774-8793,8848`); only a sourceless send can report `sent`, after dispatch. So an agent-to-agent send never reads `sent`: the shim reports it as **accepted (exit 5)** and the only proof of delivery is the peer's ack. A sourceless send runs with `clearPendingPermissions: true` (`agent-prompt.ts:32`): it answers the target's pending permission cards with the message text, so the shim refuses a target with pending permissions (fail closed on `paseo agent inspect`'s `PendingPermissions`). `--behavior steer` on a provider that cannot steer replaces the running turn (`agent-prompt.ts:38-60`); the shim holds a busy target whose `Capabilities` lack steering.
