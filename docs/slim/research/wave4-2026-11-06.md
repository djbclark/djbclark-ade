## 1. Claude Code `claude -p` (2.1.319, the latest, published 2026-11-06 00:58Z)

1. **Flags that exist** (cli-reference and `claude --help`): `--json-schema` (print mode; an invalid schema is an error; `format` keywords are annotations), `--output-format text|json|stream-json` (`stream-json` needs `--verbose`), `--settings <file or inline JSON>` (2 MiB max; above user/project/local, below managed), `--setting-sources user,project,local` (`""` accepted and means no file sources, tested; the SDK's `settingSources: []`; managed policy loads regardless), `--allowedTools` (auto-approves, does NOT restrict), **`--tools "Read,Grep,Glob"` restricts the built-in tools** (`""` disables all; MCP tools unaffected; on Linux the `default` set leaves out Glob and Grep, so name them), `--disallowedTools` (`"mcp__*"` removes all MCP tools), `--strict-mcp-config` (with no `--mcp-config` → `mcp_servers: []`, tested), `--mcp-config`, `--permission-mode default|acceptEdits|plan|auto|dontAsk|bypassPermissions` (`manual` aliases `default`), `--max-turns`, `--add-dir`, `--no-session-persistence` (print mode; nothing written under `~/.claude` for the run), `--bare` (skips hooks, skills, plugins, MCP, CLAUDE.md, memory; keeps Bash and file tools), `--restricted` (2.1.248: removes command tools and WebFetch, confines file tools, managed settings and `--settings` only, refuses bypass; **its init still listed WebSearch, Write, Edit**: not a substitute for the explicit boundary).
2. **`permissions.blockReadsOutsideWorkingDirectories`** (boolean, ≥2.1.257; tested with `--setting-sources ""` plus the key in `--settings`): `Read /etc/hostname` denied ("outside <cwd>; the permissions.blockReadsOutsideWorkingDirectories setting blocks reads…"), denied again under `--permission-mode bypassPermissions`, `./in.txt` read fine. Covers Read, Grep, Glob, LSP; NOT Bash or MCP. Exempt: skills, plugins, rules, agents, commands, and `~/.claude/CLAUDE.md`. `true` in any file applies, `false` is ignored. The denial appears in the result event's `permission_denials[]`. **Changes E8**: (a) with Bash out of the tool set the confinement is complete; (b) `--add-dir` directories count as working directories, never pass it; (c) the `~/.claude/CLAUDE.md` exemption is real; whether it loads under `--setting-sources ""` was not tested: read the init event or use `--bare`.
3. **WebFetch/WebSearch removable**: `--tools "Read,Grep,Glob"` gave init `tools: ["Glob","Grep","Read","StructuredOutput"]` (tested). **`--json-schema` injects `StructuredOutput`**, so the tripwire's allowed set is `{Read, Grep, Glob, StructuredOutput}` (the plan's "four read tools" named `LS`, which is not a 2.1.319 tool). Assert the allow-list from init, not a deny-list.
4. **`--settings` JSON** `{"hooks":{},"permissions":{"deny":[...],"blockReadsOutsideWorkingDirectories":true,"disableBypassPermissionsMode":"disable"},"disableAllHooks":true}` accepted (tested). `hooks: {}` empties only that layer: add `disableAllHooks: true`. Managed settings load regardless of `--setting-sources`, so a managed hook would survive: assert from the run's output that none is present.
5. **Init event** (`{"type":"system","subtype":"init"}`, schema `SDKSystemMessage`): `tools[]`, `mcp_servers[{name,status,source?}]`, `permissionMode`, `cwd`, `model`, `apiKeySource`, `claude_code_version`, `plugins[]`, `skills[]`, `slash_commands[]`, `agents[]`, `capabilities[]`. It is **not the first line** (`active_goal` and `autocompact_state` precede it). Tool use is visible in `assistant`/`user` events; the `result` event has `structured_output`, `permission_denials`, `num_turns`, `is_error`.
6. **Bypass is not refused, it is silently downgraded** (tested): `--permission-mode bypassPermissions` with `disableBypassPermissionsMode:"disable"` exited 0 with init `permissionMode: "acceptEdits"`. **Changes E8**: the launcher refuses bypass itself (flag, env or settings) before the run and asserts init's `permissionMode` is exactly the expected value. `bypassPermissions` in project/local settings is ignored since 2.1.257.
7. **Built-in plugins, skills and agents appear in init even with `--setting-sources ""`** (`cc-plugin-*@builtin`, `verify`, `debug`, `code-review`, `batch`, Explore, general-purpose). Do not assert that `skills`, `slash_commands` or `agents` are empty; assert `tools`, `mcp_servers` and the reads.
8. `--restricted`: see item 1; not relied on.
9. Auth in `-p` works with `apiKeySource: "none"` (OAuth). No change.

## 2. Paseo CLI 0.15.3 (the latest, published 2026-11-06 15:37Z; `--help` is richer than the docs page)

10. **`paseo run`**: the prompt is positional and required; **no `--prompt-file`** (only `paseo send` has it). Flags: `--no-wait`, `--title`, `--provider <p or p/model>`, `--model`, `--thinking <id>`, `--mode <mode>`, `--cwd`, `--workspace <id>`, `--new-workspace local|worktree`, worktree flags, `--image`, `--env k=v`, `--label k=v`, `--wait-timeout <duration, e.g. 30s>`, `--output-schema <file or inline>` (**not with `--no-wait`**), `--json`, `-q`, `--host`/`--home`. `--wait-timeout` takes a duration, `paseo wait --timeout` takes seconds. **Changes E6**: the shim passes a short prompt as argv that names the brief file, or creates the agent and follows with `send --prompt-file`.
11. **`paseo wait <id> [--timeout S] [--json]`** statuses idle | timeout | permission | error; exit codes per status not confirmed: the shim maps from the status field (124, 77, …), never from `$?`.
12. **`paseo provider ls --json`** (tested): flat array `{provider, label, status, enabled, defaultMode, modes}`; `status` is `loading` right after daemon start, then `available | unavailable | error` (the registry must retry or wait); `enabled` is the string `"Enabled"`/`"Disabled"`; **`modes` is a comma-joined string of labels** ("Plan Mode, Always Ask, Accept File Edits, Auto mode, Bypass"), not ids. Provider ids seen: claude, codex, copilot, opencode, pi, omp, antigravity, muse. Models: `paseo provider models <provider> --json` → `{model, id, description, thinkingOptionIds[], defaultThinkingOptionId}`. Also `paseo provider diagnostic <p> [--json]`. **Changes E7**: status and enabled from `provider ls`, model ids from `provider models`, mode ids from `paseo agent mode <id> --list`.
13. **`paseo usage ls --json`** (tested, confirms wave3 item 6): array of `{id ("copilot:default"), sourceId, sourceLabel, icon (inline SVG, strip it), account, fetchedAt, report, loginErrors[]}`; `report.status` can be `unavailable` with `problem:{kind:"rejected",status:403}`, exit 0. Flags `--refresh`, `--agent <id>`, `inspect <report-id>`. **Changes E7, minor**: an unavailable or error report is "unknown", never a pass.
14. **Permission mode ids per provider** (source): Claude `plan`, `default` ("Always Ask"), `acceptEdits`, `auto`, `bypassPermissions` (alias `bypass`); **Claude's `defaultMode` is `auto`**, so a `paseo run` with no `--mode` is not read-only; `plan` is the only non-editing Claude mode and is not "deny all tools". Codex lists `auto`, `auto-review`, `full-access`; `read-only` appears in source as a sandbox/approval mapping (sandbox `read-only`, approval `on-request`) but **`--mode read-only` for codex is unverified** (codex unavailable in the researcher's environment): check with `paseo agent mode <codex-id> --list`. **Changes E6**: always pass `--mode`.
15. **No per-run tool set or MCP config through Paseo** (source). Provider-level overrides only: for Claude `{allowedTools, disallowedTools, additionalDirectories, extraArgs, sandbox, settings:{permissions:{allow,ask,deny}, sandbox}}`, `.strict()` (so `blockReadsOutsideWorkingDirectories` and `hooks` are rejected in `settings`; `extraArgs` is `Record<string,string|null>` and `extraArgs.settings` can name a settings file, which is merged); Paseo's Claude provider hardcodes `settingSources: ["user","project","local"]`. Per-agent MCP servers/tools/env come only from a plugin's `agent.open.before` hook. **Changes E6 materially**: `--perm read-only|deny` through `paseo run` is only as strong as the provider mode and does not carry the review boundary; the boundary stays in `bin/review-launch` (direct `claude -p`).

## 3. GitHub

16. **`pull_request_target` is blocked by default in PUBLIC repositories from 2026-12-02** (github.blog/changelog/2026-11-02-pull_request_target-blocked-by-default-december-2, read today): evaluate mode until then, **brownouts 16:00–18:00 UTC on 2026-11-09 and 2026-11-16** when blocked runs fail; private/internal repos unaffected; allowed only by an Actions event policy with workflow-file targeting (the exact policy UI/API path was not found). `gh api repos/djbclark/djbclark-ade`: `private:false, visibility:"public", default_branch:"master"`. **Stops E8's Action as planned.**
17. **`pull_request_target` ref semantics** (changelog 2025-11-07, effective 2025-12-08): `GITHUB_REF`/`GITHUB_SHA` are now the **default branch** and its last commit (the "base branch" behaviour is GHES < 3.20 only); the workflow file is always read from the default branch; an environment's deployment-branch rule matches `GITHUB_REF`, so a `pull_request_target` run of any PR, fork included, evaluates as `master` and can reach a `master`-only environment. The secret is protected only by the trusted workflow never running PR code. Not run; a hazard to design around.
18. **Rulesets, required status checks**: `required_status_checks[]` of `{context (required), integration_id (optional int)}`, `strict_required_status_checks_policy`, `do_not_enforce_on_create`. Checks and commit statuses both count; with a specific app selected, a status from any other source blocks merging. UI caveat: an app is selectable only if installed with `statuses:write` and it recently submitted a check run; the API takes `integration_id` directly. **Not verified** that a commit status (not a check run) from the App matches `integration_id`: test with a throwaway PR.
19. **Create status**: `POST /repos/{owner}/{repo}/statuses/{sha}` with `state` (error|failure|pending|success), `target_url`, `description`, `context` (case-insensitive); 201; at most 1000 statuses per SHA and context. The App permission is "Commit statuses: write" (not re-read from docs today).
20. **`actions/create-github-app-token`**: latest **v3.3.0 (2026-10-12)**; v3 needs Node 24, dropped custom proxy handling (`NODE_USE_ENV_PROXY=1`), self-hosted runner ≥2.327.1; v3.1.0 added `client-id` and deprecated `app-id`; v3.2.0 allows full repository names. Pin a full commit SHA. **Changes E8, minor**: use `client-id`.

## Lead's reading (2026-11-06)

- **E8 Action trigger (items 16, 17)**: `pull_request_target` is replaced by **`workflow_run`** (on the completion of the `pull_request`-triggered `Tests` workflow) plus **`workflow_dispatch`** (input `pr`, for re-runs after a body edit, which `workflow_run` cannot see). `workflow_run` is GitHub's documented trusted-post-processing trigger: the workflow file and ref are the **default branch** (so the `master`-only `merge-gate` environment is reachable by it and NOT by any `pull_request` run, whose ref is `refs/pull/N/merge`: property (b) of PLAN E8 holds, now by documented semantics), nothing from the PR is checked out, and a PR that edits or removes the triggering workflow gets no status, which fails closed. The PR is found by head SHA (`GET /repos/{o}/{r}/commits/{sha}/pulls`, plus the event's `pull_requests[]` when present), the body and head re-read through the API just before posting, and the status posted only when the head is unchanged. The body-edit re-run becomes one lead command after writing the marker: `gh workflow run adversary-marker.yml -f pr=N`. Everything else in PLAN E8 (App-minted status, `integration_id` pinned in the ruleset, read-only `GITHUB_TOKEN`, the spoofing-workflow tests, the ported marker tests) stands. The `pull_request_target` Actions event policy is NOT used: it is a setting GitHub is pushing against and its path is unknown from here.
- **E8 review-launch (items 2–7)**: allowed tool set `{Read, Grep, Glob, StructuredOutput}` via `--tools "Read,Grep,Glob"` plus `--json-schema`; `--settings` JSON with `disableAllHooks: true`, `blockReadsOutsideWorkingDirectories: true`, deny rules as the second layer; `--setting-sources ""`, `--strict-mcp-config`, `--no-session-persistence`, no `--add-dir`; `--permission-mode default` (never bypass; the launcher refuses a bypass flag/env/setting before the run and asserts init's `permissionMode`); the init event is found by `subtype == "init"` wherever it falls; assert `tools` and `mcp_servers` exactly, never that skills/agents are empty; record the `~/.claude/CLAUDE.md` exemption as accepted (or launch with `--bare` and record which).
- **E6 shim (items 10, 11, 14, 15)**: the shim's Claude restricted modes are `bin/review-launch`'s modes (direct `claude -p`, not `paseo run`), as PLAN E6 already says; for every other provider `--perm read-only` maps to a verified provider mode (`paseo agent mode <id> --list` at launch, fail closed on a mode not listed) and is documented as weaker than review-launch; `--perm deny` is refused for providers with no non-editing mode. `--mode` is always passed (Claude's default is `auto`). The prompt is argv (a one-line pointer to the brief file plus the footer; the brief itself is read by the agent), never `--prompt-file`. `--output-schema` cannot pair with `--no-wait`: the shim runs `paseo run --no-wait --json`, records the agent id, and `paseo wait <id> --timeout S --json` maps the status field to the exit-code contract.
- **E7 (items 12, 13)**: the registry reads `paseo provider ls --json` (retry while `loading`; `enabled == "Enabled"` and `status == "available"`), `paseo provider models <p> --json` for model ids; the frontier gate reads `paseo usage ls --json` with `report.status != "available"` as unknown (fail closed for `frontier`, pass-through for other kinds as today's stale-state rule).
