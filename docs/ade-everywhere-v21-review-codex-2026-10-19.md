## 1. Verdict

**Ready to begin Phase 0 preservation and classification, with an explicit backup gate before replacing any existing config or link; not ready to implement the Phase 1–3 interfaces as written.** The earlier review materially improved the plan: Hermes is preserved, live SQLite replication is rejected, forks replace offline leases, the first slice includes real Linux, retirement is gated, and Paseo work targets the missing capabilities. However, the specified chezmoi external is not a private source-state overlay, chezmoi does not retain the promised originals, the encrypted peer cannot do its assigned plaintext indexing, and the new takeover handshake still permits two owners. CASS needs a validated materialized input view and a measured resource budget; the proposed generation layout is neither a transparent adapter input nor a bounded storage policy. These are targeted corrections to the decided design, not reasons to restart the tool selection.

## 2. Findings

Severity meanings: **blocker** prevents the named next action from safely or correctly implementing the proposal; **major** risks data loss, incorrect behavior, or substantial rework at the named phase gate; **minor** is a factual/documentation correction with a narrower effect. Later-phase findings do not block initial preservation.

### F1 — blocker — The promised chezmoi rollback copies do not exist

**Claim:** T1 says “chezmoi keeps the originals it replaced” ([proposal:38](/Users/djbclark/src/djbclark-ade/docs/ade-everywhere-proposal.md:38)); §4.4 repeats “chezmoi keeps the replaced originals” ([proposal:240](/Users/djbclark/src/djbclark-ade/docs/ade-everywhere-proposal.md:240)). Phase 0 already includes fixing links and adopting config templates ([proposal:556](/Users/djbclark/src/djbclark-ade/docs/ade-everywhere-proposal.md:556)).

**Verified:** Chezmoi's target application compares content hashes, removes an incompatible target type, and writes the new contents. Its own implementation explains that full old contents are not stored. The `apply` conflict prompt is not a backup or an undo journal. See [TargetStateFile.Apply, lines 202–239](https://github.com/twpayne/chezmoi/blob/cd643211529b8e849d86f2a89b2eb3005adc3cfd/internal/chezmoi/targetstateentry.go#L202) and [apply reference](https://www.chezmoi.io/reference/commands/apply/).

**Recommendation:** Before the first replacement, take an explicit private adoption snapshot containing original bytes, modes, symlink targets and absence records; record what each apply changed and how to restore it without overwriting subsequent user changes. Keep this outside the public source state. Change T1 to require ADE's adoption/rollback procedure, rather than attributing it to chezmoi. This is the only immediate stop condition for the mutating part of Phase 0; classification and backup can proceed.

### F2 — blocker — `.chezmoiexternal` is not the specified private source-state overlay

**Claim:** §4.4 says “`.chezmoiexternal` pulls the companion's `home/` overlay so private files win where both define a path” ([proposal:230](/Users/djbclark/src/djbclark-ade/docs/ade-everywhere-proposal.md:230)). §12 claims an `overlay.toml` contract with precedence, keyed merges and unknown-key rejection ([proposal:814](/Users/djbclark/src/djbclark-ade/docs/ade-everywhere-proposal.md:814)).

**Verified:** External entries name **targets**. Archive members are installed as target content; a git-repo external clones into the destination. They do not recursively interpret a second repository's `dot_`, `modify_`, `symlink_`, and `.tmpl` source attributes as another chezmoi source layer. The implementation still explicitly marks source-format externals as unimplemented; its duplicate canonicalization coalesces equivalent directories, not an arbitrary private-wins merge of files. See [external reference](https://www.chezmoi.io/reference/special-files/chezmoiexternal-format/) and [source-state implementation](https://github.com/twpayne/chezmoi/blob/cd643211529b8e849d86f2a89b2eb3005adc3cfd/internal/chezmoi/sourcestate.go) (archive handling around 2570–2655; duplicate handling around 3105). The proposal mentions `overlay.toml` only in its response table; it does not actually define that file, merge keys, deletion semantics, or validation rules.

**Recommendation:** Before Phase 1, specify **one effective source state**. Prefer public templates that read validated companion data, plus an explicit mechanism for private-only files. If arbitrary private source files must replace public source files, assemble a deterministic source tree before invoking chezmoi; that composition is ADE functionality with tests. Two independent chezmoi instances are possible for disjoint targets, but overlapping ownership requires explicit sequencing and conflict rules and is not the promised single-owner solution. Use externals for actual external target assets.

Also declare `.chezmoiroot` containing `home`, use `symlink_...` sources containing the intended link target, and template OS-specific target exclusions in `.chezmoiignore`. Ignoring a path is not an uninstall/ownership-transfer operation. Restore the explicit public < private < role < machine data precedence, stable keys for arrays, deletions, and unknown-key handling before generating any manifests. [Source-root reference](https://www.chezmoi.io/reference/special-files/chezmoiroot/), [ignore reference](https://www.chezmoi.io/reference/special-files/chezmoiignore/), [chezmoi design rationale](https://www.chezmoi.io/user-guide/frequently-asked-questions/design/).

### F3 — major — Bootstrap still starts after its prerequisites, credentials and trust verification are needed

**Claim:** §4.4 promises “only prerequisites are git and a shell,” starts with `chezmoi init --apply`, installs packages second, creates a missing companion third, and signs into secrets fourth. Chezmoi itself is “installed from the pinned package list”; signed tags are the newcomer trust anchor ([proposal:226](/Users/djbclark/src/djbclark-ade/docs/ade-everywhere-proposal.md:226), [proposal:264](/Users/djbclark/src/djbclark-ade/docs/ade-everywhere-proposal.md:264)).

**Verified:** This is a dependency cycle in the stated sequence. First apply can need a nonexistent private repository, private-fetch authentication, secret template data, and the not-yet-installed chezmoi/runtime. A signed tag does not authenticate an unknown signer merely because it is signed, and executing the bootstrap before verifying it does not solve that problem. Chezmoi publishes prebuilt binaries and a checksum/signature verification procedure; adopting it still requires declaring the initial verification tools and trusted key source. [Chezmoi installation and verification](https://www.chezmoi.io/install/).

**Recommendation:** Phase 1 needs a small stage-zero contract: supported OS/architecture and system utilities; authenticated bootstrap revision/key fingerprint; acquire the pinned chezmoi artifact with verification; establish or skip the companion; establish required credentials; then validate and apply. Public-only/`none` must succeed without attempting private fetches or evaluating secret-dependent templates. Creating a remote repository needs an explicit forge credential path, while a local-only empty companion should work without one. Either support the literal git-and-shell promise or amend it to the actual minimal system prerequisites. Do not postpone the release/signing procedure until Phase 7 when Phase 1 depends on it.

### F4 — major — Owned-key merging is not concurrent-writer safety, and HOME ownership is contradictory

**Claim:** §4.4 makes `modify_` scripts merge only ADE keys and calls this “the only safe contract”; the same section calls existing Ansible roles but says “Ansible never touches `$HOME` once chezmoi does” ([proposal:235](/Users/djbclark/src/djbclark-ade/docs/ade-everywhere-proposal.md:235), [proposal:245](/Users/djbclark/src/djbclark-ade/docs/ade-everywhere-proposal.md:245), [proposal:278](/Users/djbclark/src/djbclark-ade/docs/ade-everywhere-proposal.md:278)).

**Verified:** `modify_` reads existing target content and produces replacement content. It is a read/modify/write transformation, not a lock shared with Paseo or Claude. If another writer changes an unowned key between the read and replacement, ADE can erase that change. Idempotency also depends on the script, especially array merges and deletions. [Chezmoi modify-file semantics](https://www.chezmoi.io/user-guide/manage-different-types-of-file/). Existing Ansible roles demonstrably install HOME scripts, configuration and LaunchAgents ([inventory:150](/Users/djbclark/src/djbclark-ade/docs/ade-everywhere-inventory-2026-10-19.md:150), [inventory:160](/Users/djbclark/src/djbclark-ade/docs/ade-everywhere-inventory-2026-10-19.md:160)); `ade services` itself writes user units/plists there.

**Recommendation:** Define ownership **per path and JSON key**, not by the whole HOME directory. Separate package-only Ansible tasks from config writers before invoking existing roles. For shared JSON, quiesce the application's writer during apply or use a supported mutation interface with a proven concurrency protocol; an ADE-only lock cannot constrain an unrelated writer. Require pure transforms, `f(f(x)) = f(x)`, preservation of unowned keys, stable keyed-list semantics, explicit removal of formerly managed entries, and fail-closed parsing. Treat `diff`/`verify` evaluation as side-effect-free. Schedule this in Phase 1, including the later Paseo config boundary; Phase 4 can widen the covered keys.

### F5 — major — “Stopped at generation N” is an observation, not an exclusive transfer

**Claim:** §6.3.6 allows same-ID takeover when the origin answers “stopped at generation N” ([proposal:438](/Users/djbclark/src/djbclark-ade/docs/ade-everywhere-proposal.md:438)).

**Verified counterexample:** B and C concurrently ask A to take a stopped session. A can truthfully acknowledge both. Both resume the same ID. A sequential variant also survives: A transfers to B, then C asks historical origin A, which is still stopped although B is active. An old host's quota/reboot resume machinery can also restart a relinquished session; such machinery already exists in [README:68](/Users/djbclark/src/djbclark-ade/README.md:68) and [acp-run dispatch controls:499](/Users/djbclark/src/djbclark-ade/tools/acp-run/README.md:499). This is a protocol counterexample, not a claim that an experiment was run. Syncthing cannot serialize these decisions, as the proposal now correctly recognizes. [Synchronization semantics](https://docs.syncthing.net/users/syncing.html).

**Recommendation:** Phase 2 needs a durable, serialized transfer record bound to the expected current owner, ownership epoch, recipient device, transfer ID and final generation. Freeze launch/reaper/auto-resume paths, stop the provider, capture its final complete state, persist relinquishment, and acknowledge that specific recipient. Define retries, lost acknowledgements, crashes before activation, and subsequent transfers. Never infer ownership from “origin is not running.” If unwrapped native launches cannot be fenced, scope the guarantee to ADE-managed sessions and state that limitation; otherwise retain fork-only behavior for those cases. Preserve the decided unreachable-origin behavior: fork, not same-ID takeover.

### F6 — major — A marker written last locally is not a committed generation on another device

**Claim:** §6.3 defines a generation by size, SHA-256 and “a completion marker written last,” with transcript sidecars beside it; pull selects the latest complete generation ([proposal:398](/Users/djbclark/src/djbclark-ade/docs/ade-everywhere-proposal.md:398), [proposal:431](/Users/djbclark/src/djbclark-ade/docs/ade-everywhere-proposal.md:431)).

**Verified:** Syncthing can pull files in random, alphabetical, size or time order, and sorting applies only to discovered batches. It does not preserve the writer's cross-file publication order. A small marker can arrive before the transcript or a large sidecar. [Syncthing `order` configuration](https://docs.syncthing.net/users/config#config-option-folder.order). Hashing a completed copy also does not prove a consistent source snapshot if a non-APFS source is rewritten while being copied; it proves the copied bytes' integrity.

**Recommendation:** Define a versioned generation manifest listing **every required object**, its hash and size, provider format version, parent generation and capture status. A receiver must validate the entire manifest before making the generation eligible for pull or indexing. Stage a verified local view outside CASS's visible roots and publish it atomically. For ordinary file copies, detect concurrent replacement/rewrite and retry or quiesce; define a complete-record cutoff for appenders and retain uncaptured tail status. Do not claim multi-file consistency from a single-file clone. Phase 2 acceptance must include marker-first delivery, missing sidecars, truncated transfers, source compaction during capture, and crash recovery. This closes a remaining hole in the v1 collector remedy rather than repeating the already-fixed hardlink problem.

### F7 — major — CASS path maps do not implement the proposed archive/export adapter

**Claim:** §6.3.4 points CASS directly at the archive with “a per-provider path map per device,” says OpenCode's adapter only finds `.opencode/`, and assumes a collector export feeds any otherwise unsupported store ([proposal:423](/Users/djbclark/src/djbclark-ade/docs/ade-everywhere-proposal.md:423)).

**Verified:** CASS has local source roots as well as SSH/rsync mirrors and source provenance. Path mappings translate source workspace paths; they are not a universal file-layout or export-format conversion layer. OpenCode's actual connector supports `OPENCODE_SQLITE_DB` and explicitly probes `~/.local/share/opencode/opencode.db`. Hermes also has a native SQLite connector. The CASS v0.10.0 OpenCode and Hermes modules re-export `franken-agent-detection` connectors; the exact dependency is `=0.3.3`. [CASS Cargo manifest](https://github.com/Dicklesworthstone/coding_agent_session_search/blob/v0.10.0/Cargo.toml), [OpenCode module](https://github.com/Dicklesworthstone/coding_agent_session_search/blob/v0.10.0/src/connectors/opencode.rs), [versioned connector source](https://docs.rs/crate/franken-agent-detection/0.3.3/source/src/connectors/opencode.rs), [source configuration](https://github.com/Dicklesworthstone/coding_agent_session_search/blob/v0.10.0/src/sources/config.rs).

The matching crate source was downloaded and inspected: OpenCode candidate paths are at lines 137–181 in `evidence/fad033-opencode.rs`. A vendor JSON export does not necessarily match a connector's expected database or session/message/part directory structure. Upstream itself found remote mirror layout and cross-provider misattribution bugs, with fixes on main announced after v0.10.0. [CASS issue 520](https://github.com/Dicklesworthstone/coding_agent_session_search/issues/520).

**Recommendation:** Keep CASS, but put a documented **derived native-shaped view** between the immutable archive and its connectors. Give each device/source stable provenance and each provider only its intended roots. Materialize consistent SQLite backups where supported; implement format conversions only where actually needed. Use per-connector overrides where available. A separate adapter/materializer can avoid a CASS fork; direct ingestion of the proposed arbitrary tree is not established. Phase 2 must prove source IDs, workspace mapping, message coverage, no provider misattribution, repeat indexing, and a second generation. Do not make “export exists” the acceptance criterion.

**Adapter coverage actually advertised in the inspected release:** Codex, Cline, Gemini, Claude Code, Clawdbot, Vibe, OpenCode, Amp, Cursor, ChatGPT, Aider, Pi, Prime, OMP, Copilot Chat, Copilot CLI, OpenClaw, Goose, Crush, Hermes, Devin, Shelley, Grok Bot, Kimi, Muse, Qwen, Factory, Antigravity, OpenHands, Grok Build, Codebuff/Freebuff, and Kiro. This is 32 connectors, not 32 interchangeable native formats. zcode is not named. Cursor editor storage is not automatically Cursor CLI storage; similar checks apply to the installed Cline/Qwen variants. [Release connector inventory](https://github.com/Dicklesworthstone/coding_agent_session_search/blob/v0.10.0/README.md#supported-agents).

### F8 — major — Full generations multiply both storage and indexed conversations; the 10 GB estimate is not the capacity model

**Claim:** Each capture of a grown file creates `<session-id>/<generation>.jsonl`; hot retention is one year, and §11 treats indexing as roughly “10 GB of small files” ([proposal:400](/Users/djbclark/src/djbclark-ade/docs/ade-everywhere-proposal.md:400), [proposal:461](/Users/djbclark/src/djbclark-ade/docs/ade-everywhere-proposal.md:461), [proposal:773](/Users/djbclark/src/djbclark-ade/docs/ade-everywhere-proposal.md:773)).

**Verified:** The Claude connector's ordinary-file external ID derives from its relative path, while the native session ID is metadata (`evidence/fad033-claude_code.rs:943–968`). CASS conversation uniqueness includes source, agent and external ID. Thus changing the generation filename can create another conversation rather than update the same one. [Claude connector source](https://docs.rs/crate/franken-agent-detection/0.3.3/source/src/connectors/claude_code.rs), [CASS storage](https://github.com/Dicklesworthstone/coding_agent_session_search/blob/v0.10.0/src/storage/sqlite.rs).

The backup cost also grows independently of indexing: with n equally spaced growth captures ending at size S, whole-file snapshots total approximately S(n+1)/2. For example, 100 captures ending at 100 MB total about 5.05 GB. APFS sharing saves local blocks, but the encrypted Syncthing peer cannot reuse blocks **between different files**. [Encrypted-device caveats](https://docs.syncthing.net/users/untrusted.html#caveats).

CASS adds its own archive/index/mirror costs. Issue 522 contains a maintainer reproduction of v0.10.0 repeatedly mirroring whole growing transcripts, and subsequent chunking/budget fixes on main. Those fixes must not be assumed in a release binary solely because current documentation describes them. [Issue 522](https://github.com/Dicklesworthstone/coding_agent_session_search/issues/522), [latest release metadata](https://api.github.com/repos/Dicklesworthstone/coding_agent_session_search/releases/latest). Published CASS documentation also describes automatic background repair on search and multi-million-message rebuilds with double-digit-GB RSS; these are warnings about sizing, not a benchmark of this corpus. [Release README, scheduling and resource controls](https://github.com/Dicklesworthstone/coding_agent_session_search/blob/v0.10.0/README.md).

**Recommendation:** Keep immutable recovery generations but define chunk/checkpoint retention and budget their physical replicated bytes. Index one stable materialized latest version per logical conversation; expose historical generations separately. Decide whether ADE's authoritative archive makes CASS raw mirroring redundant, and verify the chosen binary's controls before disabling it. Pin a tested release/commit and record a representative full rebuild's wall time, peak RSS, database/index/mirror sizes and incremental growth. Put Mac search in strict read-only/no-maintenance mode during working hours; the documented `search --no-maintenance` and `CASS_AUTO_REFRESH=0` are candidates to confirm against that pin. Schedule actual rebuilds through the load policy. No credible exact 10 GB rebuild duration can be inferred from the proposal or upstream headline query latency.

### F9 — major — The ciphertext-only Linux peer cannot perform its assigned index and export work

**Claim:** Q2 selects vps-primary; §6.3.3 says it “stores ciphertext only.” Yet Phase 3 and §11 assign the first full CASS index and Hermes export to “the Linux peer” ([proposal:417](/Users/djbclark/src/djbclark-ade/docs/ade-everywhere-proposal.md:417), [proposal:579](/Users/djbclark/src/djbclark-ade/docs/ade-everywhere-proposal.md:579), [proposal:752](/Users/djbclark/src/djbclark-ade/docs/ade-everywhere-proposal.md:752), [proposal:773](/Users/djbclark/src/djbclark-ade/docs/ade-everywhere-proposal.md:773)).

**Verified:** Receive-encrypted storage hides file contents, names and directory structure; ordinary CASS connectors cannot index it. Decryption belongs on a trusted device. [Syncthing encrypted devices](https://docs.syncthing.net/users/untrusted.html). A SQLite backup must originate through access to the source database, and a Hermes export on another host requires a readable consistent copy or a purpose-built remote operation. [SQLite backup API](https://www.sqlite.org/backup.html).

**Recommendation:** Split the compute table into trusted plaintext workers, ciphertext storage, and source-local capture. Preserve Q2 by using Mac off-hours for private indexing unless the operator explicitly designates a separate trusted Linux worker. Another account on the same administrator-controlled VPS is not a confidentiality boundary against that host. Ciphertext Syncthing scanning can run there; plaintext export/indexing cannot. Public CI builds and permitted agent jobs are a separate workload. The route manifest should declare required data, credentials, OS, runtime and workspace availability before sending a slice remotely; a model's quota availability does not provision those resources.

### F10 — major — The stated loss window omits uncollected data and collected-but-unreplicated generations

**Claim:** T4 says loss is at most what the device “collected since its last sync,” then calls the recovery point “last collection.” §6.5.4 repeats this ([proposal:48](/Users/djbclark/src/djbclark-ade/docs/ade-everywhere-proposal.md:48), [proposal:471](/Users/djbclark/src/djbclark-ade/docs/ade-everywhere-proposal.md:471)).

**Verified counterexample:** A syncs generation 1, collects generation 2 while offline, produces more messages after collection, then is lost. B can recover only generation 1. The loss includes both generation 2 and everything never collected. Even a successful “collect before closing the lid” does not prove another device possesses the generation. Asynchronous replication is explicitly documented. [Syncthing synchronization](https://docs.syncthing.net/users/syncing.html).

**Recommendation:** Honor Q15 by defining the recoverable boundary as **the latest complete collection verified on a surviving independent device**. Report separate last-captured and last-replicated generation/timestamps, per provider; do not use one green status for both. Before-lid collection may reduce the capture gap but needs replication acknowledgement to reduce the disaster-recovery gap. Fix T4 and §6.5; add an offline-and-lost-origin acceptance case in Phase 3. This is a terminology and observability correction to the accepted loss-window policy, not a demand for zero data loss.

### F11 — major — Cold-tier encryption and the strict two-copy floor are not specified

**Claim:** §6.5 selects git-annex with `numcopies 2` across the peer and a workstation and requires two copies before dropping the hot copy ([proposal:461](/Users/djbclark/src/djbclark-ade/docs/ade-everywhere-proposal.md:461)); Q2/Q7 still require a blind vps-primary peer.

**Verified:** Syncthing folder encryption does not automatically encrypt an independent annex remote. Git-annex distinguishes ordinary repositories from encrypted special remotes. Its shared-key mode stores the cipher in the Git repository, so giving that repository to an untrusted peer can defeat the intended separation. [Annex encryption](https://git-annex.branchable.com/encryption/). `numcopies` is the desired copy count; its own documentation names a concurrent-drop/special-remote-locking exception. `mincopies` supplies the hard minimum for that case. [numcopies](https://git-annex.branchable.com/git-annex-numcopies/), [mincopies](https://git-annex.branchable.com/git-annex-mincopies/).

**Recommendation:** Before Phase 5, name the encrypted special-remote type, encryption/key custody, metadata placement and restore procedure; ensure the peer lacks the decryption key. Encode the accepted two-copy floor through appropriate `numcopies`/`mincopies` and serialized deletion, not a prose interpretation of `numcopies` alone. Count independent durable copies, not two paths on one disk. Also specify Syncthing versioning strategy, retention and recovery host: versioning is per-folder/per-device, defaults off, and protects received changes rather than local changes on the same host. [Versioning reference](https://docs.syncthing.net/users/versioning.html). This supplements the already-adopted backup mechanism; it does not reopen Q7's retention duration.

### F12 — major — The Paseo route is feasible, but several listed operations have different contracts

**Claim:** §7.2 lists SDK `agents.create`, `waitForFinish`, `send`, `stop`, `--output-schema` and profiles, says acp-run “owns its processes,” and promises slices appear as subagents ([proposal:520](/Users/djbclark/src/djbclark-ade/docs/ade-everywhere-proposal.md:520)).

**Verified at Paseo 0.12.0:**

| Route requirement | Actual capability and limit |
|---|---|
| Create with cwd and model | High-level `agents.create` accepts `cwd`, config, prompt, env, labels, output schema, parent and idempotency key. Config selects provider/model and discovered mode/thinking/features. |
| Select a named profile | The high-level create type and CLI run options have no named-profile argument. Profiles are host config; the route must resolve one into explicit settings and record what it selected. |
| Send and wait | `send` acknowledges acceptance. `run`/`waitForFinish` wait for a turn; the SDK default timeout is ten minutes. Completion, permission wait, error and timeout need separate treatment. |
| Stop | CLI `paseo stop` uses lower-level `cancelAgent`; the documented high-level agent handle has no `stop()` method. Closing the SDK client closes the connection, not the agent. Stop's result must be checked, including partial failures and non-running states. |
| Permissions | Request-ID responses exist. This does not automatically reproduce acp-run's provider-specific `--perm deny` stripping, newly documented `--perm read-only` policy, tool restrictions and exit-77 behavior. Mode names are provider-specific. |
| Parent linkage | `PASEO_AGENT_ID` is resolved against the target daemon. Cross-host calls deliberately have no local caller there; an external acp-run parent may have no Paseo ID at all. |
| Structured output | CLI `--output-schema` is rejected with `--no-wait`. SDK has an `outputSchema` option, but schema output is not ADE's report-file/`.done`/`BLOCKED:` contract. |
| Cross-host | CLI host selection works with a reachable pre-existing daemon and remote cwd. The orchestration MCP tools are host-local. Remote transport does not install agents, clone workspaces or authenticate providers. |
| Existing acp-run controls | Provider-native options are validated, not arbitrary CLI passthrough. `--add-dir`, context/config controls, environment sanitization, slice deadlines, wrap-up, inbox delivery and native-session resume require individual mapping or an explicit unsupported result. |

Sources: [pinned SDK types](https://github.com/getpaseo/paseo/blob/v0.12.0/packages/client/src/index.ts#L243), [SDK reference](https://github.com/getpaseo/paseo/blob/v0.12.0/public-docs/sdk/reference.md), [CLI run validation](https://github.com/getpaseo/paseo/blob/v0.12.0/packages/cli/src/commands/agent/run.ts#L387), [CLI stop implementation](https://github.com/getpaseo/paseo/blob/v0.12.0/packages/cli/src/commands/agent/stop.ts), [caller-agent resolution](https://github.com/getpaseo/paseo/blob/v0.12.0/packages/cli/src/utils/caller-agent.ts), [provider options](https://github.com/getpaseo/paseo/blob/v0.12.0/public-docs/sdk/provider-options.md), [orchestration](https://github.com/getpaseo/paseo/blob/v0.12.0/public-docs/orchestration.md), [connectivity](https://paseo.sh/docs/connectivity). Existing ADE requirements: [acp-run controls:177](/Users/djbclark/src/djbclark-ade/tools/acp-run/README.md:177), [timeouts:207](/Users/djbclark/src/djbclark-ade/tools/acp-run/README.md:207), [dispatch slices:455](/Users/djbclark/src/djbclark-ade/tools/acp-run/README.md:455).

**Recommendation:** Write the route state machine before Phase 4 code: acp-run owns job policy; Paseo owns the routed runtime. Persist host, agent ID, native session ID, turn, attempt and idempotency token before retryable operations. After an uncertain create/send, reconnect and reconcile the original job; never silently retry through the native route. Cancel remotely on slice expiry and verify terminal state. Maintain host-qualified parent edges in ADE when native parent linkage cannot represent them. Resolve profiles explicitly and reject unsupported controls before launch. Include network loss after acceptance, daemon restart, duplicate create, waiting permissions at timeout and lost completion notification in the pilot. The adapter can be small only after these boundaries are explicit.

### F13 — major — The proposed work bundle does not yet preserve the stated dirty workspace

## 5. Questions only the operator can settle

These are decision points for implementation, not blockers to this delivered review. Most other issues above are engineering contracts the implementer can specify without asking the operator to choose a tool again.

5.5 **Physical retention budget:** What storage/transfer budget should bound immutable generations and redundant search captures while preserving the decided one-year logical hot history? This does not reopen Q7's duration; it chooses checkpoint granularity and capacity provisioning.
