# Paseo Workspace Setup & Scripts Evaluation (Carried #125)

**Date:** 2026-11-26  
**Status:** Study complete; no live `paseo.json` or `~/.paseo/config.json` changes applied.  
**Scope:** Evaluate Paseo's `paseo.json` workspace setup, lifecycle hooks, auto-terminals, service ports, and service proxy (`~/src/paseo`) across our repositories (`djbclark-ade`, `paseo`, `tendcf`, `cfengine-all`, `plektra-djbclark`, `aiuse`, `sudo-secretspec`, `superbrain`, etc.) against our existing worktree, `.worktreeinclude`, `site-public-djbclark/registry/ports.yml`, `bgrun`/CI-first, RAM, and trust rules.

## 1. Executive Verdict

**Do not adopt Paseo `worktree.setup`, `worktree.teardown`, or `worktree.terminals` across our repos.** They are redundant with our `git worktree add` + `ade_claims` + `WORKER` box workflow, bypass `bgrun` / `load-watch` / CI-first rules, add background RAM pressure on `bigmac` (32 GB), and carry untrusted-repo auto-execution risk on non-PR checkouts and same-repo PRs from non-`djbclark` authors.

**Selectively opt in ONLY to on-demand `scripts` (`type: "service"`) in genuinely `djbclark`/`frdminc`-owned, multi-worktree HTTP/web app repos** when running parallel worktree dev servers, using Paseo's default OS ephemeral `findFreePort()` allocator (with an `ephemeral_processes` pattern in `site-public-djbclark/registry/ports.yml` for any recurring listener, or a single claimed `worktrees.servicePorts.range`) and Paseo's built-in `*.localhost:7263` service proxy. Do **not** add `paseo.json` to `djbclark-ade`, `tendcf`, `cfengine-all`, `plektra-djbclark`, `aiuse`, `sudo-secretspec`, or third-party forks such as `superbrain` (`sidinsearch/superbrain`), and leave upstream `~/src/paseo/paseo.json` untouched (standing order 8).

### Note on `.worktreeinclude`

Paseo's server source (`~/src/paseo/packages/server/src`) has **no `.worktreeinclude` reader**. When creating a Paseo worktree, Paseo copies only `paseo.json` (`seedPaseoConfigFile`, `packages/server/src/utils/worktree.ts:792-802, 1250` and `packages/server/src/server/paseo-worktree-service.ts:89-94`) and expects `worktree.setup` to copy any ignored files from `$PASEO_SOURCE_CHECKOUT_PATH`. `.worktreeinclude` in this repo is read by Claude Code and `bin/ade_fork_controller.py` (and is intentionally empty here because secrets come from `sudo-secretspec`).

## 3. Comparison Against Existing ADE & Ops Rules

1. **Worktree workflow & `ade_claims` (`AGENTS.md` order 9, `docs/workspace-layout.md`):**
   Most ADE slices use explicit `git worktree add -b <branch> ~/src/<repo>-<slug>-wt origin/<base>` + `ade_claims.py new` inside the lead's reused `WORKER <repo> (<work>)` window rather than `paseo run --new-workspace worktree`. Because `worktree.setup`, `worktree.teardown`, and `worktree.terminals` only run for Paseo-owned worktrees, they are inert for our primary workflow — and using `worktree.teardown` as a rescue gate (proposed in the superseded 2026-10-30 `docs/paseo-only-rearchitecture.md`) fails on manual worktrees and upstream forks.
2. **CI-first & `bgrun` load-gating (`~/CLAUDE.md` items 34 & 37):**
   `worktree.setup` runs arbitrary shell commands directly under the Paseo daemon, completely bypassing `~/ops/site-private-djbclark/bin/bgrun`, `load-watch`, and our CI-first rule. Upstream `~/src/paseo/paseo.json` illustrates the hazard: its `worktree.setup` runs `npm ci`, `npm run build:server`, and `npm run build --workspace=@getpaseo/expo-two-way-audio` on every Paseo worktree create. Heavy installs/builds (`npm ci`, `cargo build`, `gradle`, `make`) must never auto-run on `bigmac` during worktree creation.
3. **Site port registry (`site-public-djbclark/registry/ports.yml`, `~/CLAUDE.md` item 34):**
   - **Where Paseo helps (and what `ports.yml` still requires):** Paseo's default `findFreePort()` probes `127.0.0.1:0` and hands the service a concrete ephemeral loopback port in `PASEO_PORT`, then exposes it through the already-registered Paseo daemon listener (`127.0.0.1:7263`) via Host-header routing (`*.localhost:7263`). This avoids claiming fixed per-worktree `188xx` rows when testing multiple web/API branches in parallel. However, `site-public-djbclark/bin/registry_lint.py` (`:372, 402-410`) and `ports.yml` (`:227-236, 273-296`) only exempt live ephemeral listeners whose command line matches an explicit substring in `hosts.mac.ephemeral_processes`: any recurring or reconcile-visible ephemeral dev server therefore still needs an `ephemeral_processes` pattern entry in `ports.yml` (or must remain strictly short-lived and stopped via `stop_workspace_script`).
   - **Where Paseo can violate `ports.yml`:** Fixed `port:` fields in `scripts.<name>`, unvetted `servicePorts.range` values, or scripts that ignore `HOST` / fall back to unregistered defaults can collide with registered ports. For example, upstream `~/src/paseo/paseo.json:14-26` binds `0.0.0.0:${PASEO_PORT:-6768}` (ignoring `HOST=127.0.0.1` and falling back to `6768`, which `ports.yml` assigns to `orca-app`).
   - **Proxy header caveat:** `service-proxy.ts:302-311` documents that `Host` / `x-forwarded-port` are unauthenticated client-supplied headers; this is benign on loopback `127.0.0.1:7263`, but services must not trust forwarded authority headers when fronted via Tailscale (`:3333`).
4. **RAM budget (`bigmac` 32 GB, RAM relief P1–P3):**
   `worktree.terminals` spawns persistent PTY shells/daemons automatically on worktree creation, directly conflicting with our RAM discipline. On-demand `scripts` (`start_workspace_script` / `stop_workspace_script`) are explicitly bounded and stoppable, provided agents stop them after verification.
5. **Security & upstream-fork hygiene (`AGENTS.md` Trust & order 8):**
   Paseo's `untrustedSource` gate protects only Paseo-initiated cross-repo (fork) PR/MR checkouts — not same-repo PRs from non-`djbclark` collaborators (untrusted under `AGENTS.md` Trust) and not manually cloned or checked-out untrusted branches. Adding local `paseo.json` files to third-party forks (`paseo`, `plektra-djbclark`, `cfengine-core`, `paseo-plugins-omercnet`, `superbrain`) also introduces merge carry against upstream (order 8).

## 5. Guardrails If Opting In Later

If an owned web/HTTP repo later opts into Paseo on-demand `scripts`:

1. **On-demand `scripts` only:** omit `worktree.setup` (or restrict to sub-second, zero-install metadata checks) and omit `worktree.terminals`; never put `npm ci`, `cargo build`, `gradle`, `make`, or `uv sync` in `worktree.setup`.
2. **Port-registry compliance:** leave `port` unset so Paseo allocates a concrete ephemeral loopback port via `findFreePort()` and passes it in `PASEO_PORT`, and always bind `${HOST:-127.0.0.1}:${PASEO_PORT}`. Add an `ephemeral_processes` command-line pattern in `site-public-djbclark/registry/ports.yml` for any recurring/reconcile-visible dev server (otherwise keep it strictly short-lived and stop it immediately after use). If a deterministic port block is ever preferred, claim one contiguous block in `site-public-djbclark/registry/ports.yml` first and configure `worktrees.servicePorts.range` in `~/.paseo/config.json` once.
3. **Wrap any build/test one-shot script in `bgrun`:** or keep tests on `just` + `bgrun` / CI-first.
4. **Stop services after verification:** call `stop_workspace_script` when finished so dev servers do not consume RAM on `bigmac`.
5. **No `paseo.json` in untrusted or upstream-fork repos:** keep third-party forks clean (order 8), and do not create Paseo-owned worktrees of untrusted checkouts (including same-repo PRs from non-`djbclark` collaborators, which Paseo's cross-repo `untrustedSource` gate does not block).
