## 1. The problem, measured (2026-11-21 ~14:30Z, read-only `ps` and `footprint`)

   2026-09-26 (site-private `memory/reference_claude_mcp_servers_spawn_per_session.md`: 14 sessions, ~98 processes,
   ~785 MB). It still holds. Claude Code's deferred tools (this session lists `mcp__graft__*` and
   `mcp__chrome-devtools__*` as deferred, schemas loaded through ToolSearch) save **context**, not **processes**: both

### 2.2 Proposed `config/mcp-registry.toml`

One file, the superset of [config/mcp-clients.toml](../config/mcp-clients.toml) (which today lists only the three
servers `ade-install doctor` checks). Hand-edited fields describe the server; measured fields are written only by tools.

```toml
schema_version = 1

[[server]]
id = "chrome-devtools"
transport = "stdio"                 # stdio | local-http | remote-http
command = "npx"
args = ["-y", "chrome-devtools-mcp@latest", "--autoConnect", "--no-usage-statistics",
        "--no-performance-crux", "--redact-network-headers"]
# url = "http://127.0.0.1:18796/mcp"  # for local-http / remote-http instead of command/args
owner = "per-session"               # per-session | launchd:<label> | app:<name> | remote:<vendor>
state = "per-session"               # per-session | per-repo | shared-safe | external-app
                                    # (may one process serve many clients? section 5.2)
auth = { kind = "dialog", keys = [], store = "none" }
                                    # kind: none | oauth | bearer | env | dialog; keys = NAMES only;
                                    # store: sudo-secretspec | client-oauth | none
capabilities = ["browser", "chrome", "devtools", "screenshot"]
expected = { claude = "on-demand", codex = "on-demand" }
                                    # per client: user | project:<path> | on-demand | denied | absent
doc = "docs/mcp-servers.md#chrome-devtools-mcp-added-2026-11-16"
risk = "operator browser session: cookies, logged-in tabs (mcp-servers.md Security 1-5)"

[server.measured]                   # written by tools, never by hand
footprint_mb = 119                  # footprint(1) of one session's copy, 2026-11-21
measured_at = "2026-11-21"
usage_30d = { claude_calls = 0, claude_sessions = 0, codex_calls = 0 }   # bin/mcp-usage --json
```

Rules: `id` matches the client config key; `keys` hold names, never values (the doctor already never prints `env`);
`expected` replaces `mcp-clients.toml`'s `clients` list and gains the states the doctor cannot express today
(`on-demand`, `denied`). A generated table (`bin/mcp-registry --md`, Phase 1) replaces the hand table in 2.1, and
`ade-install doctor` reads the registry instead of `mcp-clients.toml` (one file, one test that keeps them in step;
`mcp-clients.toml` is deleted in the same PR). The actual client state (what `ade_client_wiring.py` reads from each config)
is compared to `expected`, so drift such as graft's return (1.3) is a `warn` row.

## 3. Capability lookup: "which server has Y?"

Proposed `bin/mcp-find <capability|text>` over `config/mcp-registry.toml`; read-only, no network, no config writes:

```
$ bin/mcp-find photos
bezalel   remote-http  caps: connectors(googlephotos)  claude: DENIED  codex: user  hermes: user
          note: Google Photos Library API returns only app-created items since 2025-03-31 (docs/mcp-on-demand.md 4)
          instead: adb pull from the Titan 2 (site-private memory reference_phone_screenshots_via_adb.md)
$ bin/mcp-find imessage
bezalel   ... caps: imessage ...  claude: DENIED (ask operator, or use Codex/Hermes)
beeper    ... (no iMessage bridge in the 2026-08-23 get_accounts list)
```

1. Match order: exact tag, then tag prefix, then substring of `notes`; `--json` for scripts; exit 1 when nothing matches,
   so an agent knows to stop looking rather than guess.
2. For the calling client (`--client claude|codex|…`, defaulting to the one detected from the environment) it prints
   the reachability verdict: `callable`, `on-demand: <how to start it>`, `denied: ask the operator`,
   `absent in this client: use <client>`.
3. Pointers (Phase 1, instruction-file upkeep): one row in AGENTS.md's doc table (added by this PR, pointing here); a line
   in [skills/model-routing/SKILL.md](../skills/model-routing/SKILL.md)'s tool section; a short `skills/mcp-find/SKILL.md`
   whose description triggers on "which MCP/tool can …", "do we have a … server"; and one numbered line in
   `~/CLAUDE.md` / `~/AGENTS.md` ("Need a capability? `bin/mcp-find <cap>` before searching configs"). Agents stop reading
   client configs to find out, which also keeps secrets out of transcripts.

## 4. Google Photos: can bezalel read the operator's library?

**Verdict: confirmed. bezalel's `googlephotos` connection cannot read the operator's library**, except for items that
connection itself uploaded. Google's
[Updates to the Google Photos APIs](https://developers.google.com/photos/support/updates) (posted September 2024, last
updated 2025-08-28; read 2026-11-21): "These changes take effect March 31, 2025, with the `photoslibrary.readonly`,
`photoslibrary.sharing`, and `photoslibrary` scopes being removed"; "You can now only list, search, and retrieve albums and
media items that were created by your app"; "If your app needs users to select photos or albums from their entire library,
use to the new Google Photos Picker API". Calls that rely only on the removed scopes return `403 PERMISSION_DENIED` (the
API overview page words the same change as "On April 1st, 2025"). This matches the 2026-10-17 observation that
`GOOGLEPHOTOS_SEARCH_MEDIA_ITEMS` came back empty (site-private `memory/reference_phone_screenshots_via_adb.md`). No call
to bezalel or any Google API was made for this page.

Routes to the library, with limits:

1. **ADB pull from the Titan 2** (works today). `adb -s <titan2> shell ls -t /sdcard/DCIM/...`, then `adb pull` into a
   scratch dir. Covers only what is on the phone (camera roll, screenshots), not cloud-only or older items, and only while
   the phone is reachable over Tailscale ADB. No Google account involved. Best for "the photo or screenshot I just took".
2. **Google Takeout, scheduled.** The whole library as original files plus a JSON sidecar per item, in zip/tgz archives;
   "Scheduled exports: Automatically create an archive of your selected data every 2 months for one year"
   ([Google Account Help 3024190](https://support.google.com/accounts/answer/3024190)). Only the operator can request it.
   It is asynchronous (hours to days) and large, it is a snapshot six times a year, and only third parties document the sidecar
   format (e.g. GooglePhotosTakeoutHelper, stale since 2023). The only official unattended full-library route.
3. **Photos Picker API** with the operator's OAuth (`photospicker.mediaitems.readonly`). Official and current, but the
   operator picks items interactively in a Google-hosted page for every session. At most 2000 items per session
   (`maxItemCount`: "Values above 2000 will be coerced to 2000",
   [sessions reference](https://developers.google.com/photos/picker/reference/rest/v1/sessions)); `baseUrl`s "remain
   active for 60 minutes" ([media items guide](https://developers.google.com/photos/picker/guides/media-items)); `=d`
   downloads keep Exif minus location. No search: an agent cannot ask for "photos of X". Neither bezalel's connector nor
   any MCP server here offers it; building one means new code and an OAuth client.
4. **rclone `googlephotos`**: "From March 31, 2025 rclone can only download photos it uploaded"
   ([rclone docs/content/googlephotos.md](https://github.com/rclone/rclone/blob/master/docs/content/googlephotos.md));
   not a route. `rclone/gphotosdl` still depends on rclone's listing.
5. **gphotos-sync** ([gilesknap/gphotos-sync](https://github.com/gilesknap/gphotos-sync)): built on the Library API, archived
   2026-03-17; dead.
6. **Browser automation of photos.google.com** ([perkeep/gphotos-cdp](https://github.com/perkeep/gphotos-cdp),
   unmaintained since 2024-06; or `chrome-use`/chrome-devtools on the operator's logged-in Chrome). It reaches everything,
   but it drives the operator's Google session, breaks when the UI changes, and falls under mcp-servers.md's browser rules
   (the operator's yes for each use). Not recommended.

**Recommendation:** keep ADB pull (1) as the route for recent photos and screenshots, and record it in the registry under
the `photos` capability, so `bin/mcp-find photos` answers with it (section 3). If the operator wants agents to search the
whole library, the operator starts a scheduled Takeout (2) into a local folder and a separate slice indexes it locally (EXIF
and sidecar dates, optional local captions), with no Google API key and no MCP server. Picker (3) is worth building only if
a "here are these 40 photos" hand-over flow is wanted. bezalel's `googlephotos` connection is tagged
`photos:app-created-only` so no agent tries it again.

## 5. On-demand access

### 5.1 Options

What the clients do natively (docs read 2026-11-21; section 7):

1. **Claude Code** connects every configured server at session start, in the background. Tool search (on by default,
   `ENABLE_TOOL_SEARCH`, per-server `alwaysLoad`) defers tool *definitions* only: "Only tool names and server instructions
   load at session start". The one lazy *connection* is new and limited to **remote HTTP/SSE** servers with a discovery
   cache ("connects the server the first time Claude calls one of the server's tools"; v2.1.221+, gradual rollout,
   `MCP_DISCOVERY_CACHE=1` forces it). Stdio has no lazy option. Scoping knobs: project `.mcp.json`,
   `enabledMcpjsonServers`/`disabledMcpjsonServers`, per-project `disabledMcpServers` in `~/.claude.json` (toggled in
   `/mcp`), `allowedMcpServers`/`deniedMcpServers`, and `--strict-mcp-config --mcp-config FILE` per launch.
2. **Codex** per server: `enabled`, `enabled_tools`/`disabled_tools`, `startup_timeout_sec`, `required`, and
   `startup_readiness = "catalog"` (a cached catalog satisfies startup "while the server connects. Tool calls still need a
   live connection"). Every enabled server is launched at startup (inferred from the startup-catalog wording; not stated
   outright).
3. **Pi** 1.6.0 (now `earendil-works/pi`) has built-in MCP (`~/.pi/agent/mcp.json`, `.pi/mcp.json`; none exists here):
   "Pi connects every enabled server in the background when a session starts." The `pi-mcp-adapter` extension
   (MIT, v7.0.1) replaces it and is lazy: "Servers are lazy by default - they connect on first tool call", "Idle servers
   disconnect after 10 minutes (configurable)".

The three options:

| | (a) shared lazy aggregator | (b) per-session start | (c) status quo plus trimming |
|---|---|---|---|
| Shape | One local HTTP endpoint (e.g. `127.0.0.1:18810/mcp`, a launchd job) that every client points at; it spawns a stdio backend on its first tool call and reaps it when idle | A server is off by default and starts only in the sessions that ask for it: at launch (`--mcp-config`, Codex `-c mcp_servers.X.enabled=true`) or through a lazy stdio wrapper that answers the handshake from a cache and spawns the real server on the first call | Remove or disable servers nobody calls; keep the shared local HTTP servers as they are |
| Saves | Spawn cost of shared-safe stdio servers; one config line per client | All per-session cost of the servers that are off | Everything that is removed |
| Fits per-session/per-repo state (5.2)? | **No** for chrome-devtools and graft unless the proxy keys backends by client session or cwd, which none of the surveyed proxies document | **Yes**: each session still gets its own copy, only later or never | n/a |
| Failure mode | Proxy down = every proxied server down for every client at once; one more launchd job to watch | A wrapper bug hides one server in one session; the real server's first call is slower (seconds) | Someone needs a removed server: re-add it (one line) |
| Security boundary | One process holds every backend's secrets and runs every backend's code; front endpoint needs auth or loopback-only plus trust in local users (docs/threat-model.md accepts local agents as trusted) | Unchanged from today: secrets stay per client, per server | Unchanged; fewer processes holding the operator's Chrome session |
| Existing software | Mainstream proxies spawn at startup and never reap (sparfenyuk/mcp-proxy, TBXark/mcp-proxy, 1mcp, mcp-hub; MetaMCP pre-warms and is archived). Lazy and idle-reaping: **MCPJungle** (MPL-2.0, Go, ~1.6k stars; stateful mode, `SESSION_IDLE_TIMEOUT_SEC`, default never), and young projects: qualixar/slm-mcp-hub (AGPL, 6 stars), MarimerLLC/mcp-aggregator (C#, 30 min idle), Docker MCP Gateway (containers) | Stdio wrappers: **WEBGRS/mcp-lazy** (MIT, Python; cache handshake, spawn on first call, `idle_seconds`, never reaps mid-request), tkukushkin/lazy-mcp (Go, lazy, no reap); Pi: pi-mcp-adapter (lazy plus idle built in) | Native config only |

What lazy start does not fix: Claude Code shows the server as connected from the cache, so an agent cannot tell that a
first call will take seconds. chrome-devtools' Chrome Allow dialog would then appear at the first call instead of at session
start, which is better: today every new session that starts it can prompt.

### 5.2 Which servers can be shared

A shared process is only correct when the server keeps no per-client state:

1. **shared-safe**: basic-memory (state is the project DB, tools take `project`), firecrawl, crawl4ai, arxiv,
   paper-search, hermes (client-cursor events), cua-driver (thin client to its own daemon), cow, aws-mcp (per call).
   Most are already shared over local HTTP (2026-09-26 and 2026-10-12, site-private `project_shared_mcp_servers_http.md`,
   `project_load_spike_2026-10-12_shared_mcp.md`).
2. **per-repo**: graft holds one repo's graph and its working directory as process state (upstream ask
   trailhq/Graft#584). A shared copy would answer for the wrong repo.
3. **per-session**: chrome-devtools keeps the selected page and its one CDP connection as server state; two sessions
   on one copy would act on each other's selected tab. Each start also shows Chrome's Allow dialog.
4. **external-app**: Beeper Desktop, SiYuan, ExtraBar: the app is the server and is already one process.

So the 12 GB in 1.2 is in exactly the two servers a single shared process cannot serve. The answer for them is
*not starting them*, not sharing them.

### 5.3 Recommendation: (c) now, (b) for the two heavy stateful servers, (a) not yet

1. **Trim first (c).** Take `graft` out of `~/.claude.json` and `~/.codex/config.toml` again. That restores the
   2026-10-18 ruling, and the 1.3 drift shows a reconcile writes it back, so the doctor must flag the return (Phase 1).
   Saves ~3.3 GB at today's session count, for 4 calls a month that the `graft` CLI already covers. Disable or remove the
   zero-call Codex stdio entries (`ghost-os`, `cua-driver`, `cow`, `extrabar`) at the operator's choice; they are small,
   so this is tidiness, not memory.
2. **chrome-devtools becomes on-demand (b).** Remove it from user scope in Claude Code and Codex; keep it reachable two
   ways: (i) at launch, a proposed `bin/ade-worker-run --mcp chrome-devtools` flag (or a Paseo provider profile) adds a generated
   `--mcp-config` for that one session, and an interactive operator session runs `claude --mcp-config
   ~/.config/ade/mcp/chrome-devtools.json`; (ii) optionally a lazy stdio wrapper in its user-scope entry, so every
   session *sees* the tools but only the 1-in-1,000 that calls one starts Chrome's server. (ii) needs a vetted or
   in-repo wrapper (WEBGRS/mcp-lazy is the closest fit, but it is days old with 0 stars: read it, or write ~200 lines
   here, and upstream any fix, order 8). Start with (i); add (ii) only if agents miss the tool. Saves ~8.6 GB.
3. **No shared aggregator now (a).** The shared-safe servers are already one process each over local HTTP
   (basic-memory, firecrawl, crawl4ai, arxiv, paper-search, hermes). An aggregator in front of them would add a
   single point of failure and a process holding every secret, and would save almost nothing. Revisit it, with MCPJungle
   as the candidate (lazy plus idle in stateful mode, mature, MPL-2.0), when one of these happens: a new stateless
   stdio server wants to be shared; the client count grows (Pi with MCP); or one endpoint per client is wanted for
   policy (tool filtering, one place to rotate keys).
4. **Pi:** if Pi ever needs MCP, install `pi-mcp-adapter` (lazy plus idle by default) instead of the eager built-in,
   and point it at the same shared local HTTP endpoints.
5. **Claude remote servers:** once `MCP_DISCOVERY_CACHE` reaches this build by rollout, the remote servers (warpbuild,
   and bezalel if re-enabled) stop connecting at start for free; nothing to build.

### 5.4 Security boundary and secrets

1. Keys never sit in a client file. Today's literals (1.4) move to sudo-secretspec. Clients that expand environment
   references get `${NAME}` (Codex `bearer_token_env_var` / `env_http_headers`, Hermes already does it). For clients
   that cannot, a local HTTP shim reads the key from sudo-secretspec at start and adds the header, so the client sees
   only a loopback URL. Rotating the exposed keys is the operator's call, since they have sat in plain files.
2. A per-session launcher (5.3 item 2) passes no secret: chrome-devtools has none; a future keyed stdio server gets
   its key through `sudo-secretspec run` in the generated command, never in the JSON.
3. If (a) is ever adopted, the aggregator listens on loopback only, runs as the operator, gets each backend's secrets
   from sudo-secretspec at backend spawn, and is never published through Tailscale Funnel. The operator accepts that any local
   process can call it, the same trust as today's shared ports (AGENTS.md Trust).
4. `bin/review-launch`'s `--strict-mcp-config` boundary stays as it is: review sessions get no user MCP servers in any option.
