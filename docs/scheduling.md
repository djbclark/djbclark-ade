# Scheduling: one plist, three schedulers (`bin/ade-sched`, 2026-11-04)

The repo's unattended jobs (sweeps, watchers, collectors) are written as launchd plists in [`launchd/`](../launchd/) and
[`config/launchd/`](../config/launchd/). Those plists stay the **source of truth**. [`bin/ade_sched.py`](../bin/ade_sched.py)
(a library, issue #279 slice S0) and its CLI [`bin/ade-sched`](../bin/ade-sched) read a plist, fill its placeholders and
install it on whatever this machine schedules with: (Python 3.10 or later for `ade-sched` install/status/backend itself; `list`/`diff` pull the install catalog and need 3.11+ for `tomllib`, same as `pr-policy` (`context-budget-check`, which also does, runs as a Paseo schedule since 2026-11-06, not through ade-sched), so on Ubuntu 22.04, whose python3 is 3.10, install a newer Python before inventory commands; 2026-11-10):

| backend | what it writes | how it activates |
| --- | --- | --- |
| `launchd` (macOS) | the filled plist, `~/Library/LaunchAgents/LABEL.plist` | `launchctl bootout gui/UID/LABEL` (result ignored), `launchctl bootstrap gui/UID PATH` |
| `systemd` (Linux) | `LABEL.service`, plus `LABEL.timer` for a timed job, in `${XDG_CONFIG_HOME:-~/.config}/systemd/user` | `systemctl --user daemon-reload`, `enable` the timer (or service), `restart` it (a service: `restart --no-block`) |
| `cron` (fallback) | a `# BEGIN ade-sched:LABEL` .. `# END ade-sched:LABEL` block in the user's crontab | `crontab -l`, drop the old block, append the new one, `crontab -` (under a `flock` on `${XDG_STATE_HOME:-~/.local/state}/ade/ade-sched.lock`) ; each run is `mkdir -p ~/.local/state/ade && flock -n ~/.local/state/ade/LABEL.cron.lock ...` when `flock` is on PATH, so a run that outlasts its interval is not started twice (2026-11-05) |

Every generated unit and cron block starts `# generated by bin/ade-sched from <plist>; edit the plist` (the launchd copy
carries the same text as an XML comment). Edit the plist, then install again; never edit the generated file.

**The `<plist>` in that line is canonical (2026-11-13):** the repo-relative POSIX path (`config/launchd/X.plist`) when the
plist is under the ADE root (`--ade`, else the checkout `bin/ade-sched` runs from), the resolved absolute path otherwise. A
relative, absolute or symlinked spelling, and the shared checkout versus a worktree, render the same bytes, so the artifact
hash `reconcile` compares never depends on how the path was typed. The systemd units, the cron block and the launchd XML
comment all take the line from one function (`canonical_source`).

**Migration.** A job installed before this change carries `from /abs/path/X.plist`, so its on-disk file differs from the new
render by that one comment line and `reconcile` plans an `install` for it. That is safe: a loaded launchd job defers
untouched (no `bootout`, no rewrite, exit 6; `launchd_admission`) and stays deferred on every reconcile until its comment
is rewritten as below; systemd/cron jobs are reinstalled with the identical definition (a supervised systemd service is
restarted once). To adopt without a reload, rewrite only the comment line of the installed file (launchd:
`~/Library/LaunchAgents/LABEL.plist`; systemd: the unit's first line; cron: the line after `# BEGIN ade-sched:LABEL`) to the
repo-relative form, then run `reconcile`: the files now match, so the step is `adopt-ledger` (or `skip`), never a reload.

**Which jobs belong here (Paseo directive F2, [paseo-only-rearchitecture.md](paseo-only-rearchitecture.md)).** System jobs
(monitors, collectors, record reaping, watchdogs, sweeps) use launchd on the Mac and systemd on Linux, through this tool.
Judgment jobs that run an agent (triage, reports) use Paseo schedules (`paseo schedule create --cron ...`),
not ade-sched. **Every `paseo schedule create` passes an explicit `--mode`**: `auto` for Claude, `auto-review` for
Codex. A schedule run is created unattended, and with no `--mode` Paseo gives it the provider's unattended mode
(Claude `bypassPermissions`, Codex `full-access`), so a job that reads outside text would run with no guard. This
comes from Paseo 0.15.3's source, `packages/server/src/server/schedule/service.ts` and `create-agent-mode.ts`, read on
2026-11-07.

| --- | --- |

| `--ade DIR` | the checkout that fills `__ADE__` / `@ADE@`; default: the checkout `bin/ade-sched` is in |

| `--name NAME` | `reconcile`: limit to these logical job names (repeatable) |

## Inventory and drift (S4b, 2026-11-10)

`config/install.toml` carries transitional `[install.jobs]` and `[install.retired_jobs]` (the setup-plan's
`config/ade.toml [install.jobs]` home while that file is absent). Each job records `name`, `kind`
(`ade-sched` / `paseo` / `service`), `owner`, `class`, and for probeable rows a `label` (plus `plist` /
`mode` as needed). Paseo rows require an explicit `mode` (`auto` / `auto-review`).

- `ade-sched list` / `just sched-list` prints the inventory.
- `ade-sched diff` / `just sched-diff` and `just doctor` (via `ade-install doctor`) compare live
  `launchctl` / `systemctl --user` / `crontab` / `paseo schedule ls --json` to that inventory.
- **Report only (diff/doctor):** never unload or repair. Foreign and unknown owners (including
  Orca, BB, herdr, and any label not ADE-owned) are reported and left alone.
- Retired labels that reappear fail doctor; ADE-owned expected labels that are missing fail when
  a host scheduler (or paseo) is probeable. Planned rows without a label stay `planned`.
- A Paseo probe timeout or launch error, and a host-backend enumeration failure after detection,
  are `unknown` (unavailable), never a traceback and never an empty-job "all missing" false
  positive (2026-11-10).
- **Unchosen optional rows (`class` `optional`/`offered`, `chosen = false`, 2026-11-13):** doctor and `diff` stay quiet
  (`unchosen`; a live label adds "installed but unchosen"). `reconcile` plans `skip` for the row; for an **ADE-owned
  `ade-sched` or `paseo` row** (not a `service` or dependency row such as `herdr-server`, which keep the old silent path) it
  reports a live label as `installed but inventory row ... is not chosen` (report only, not "foreign"; an unchosen `paseo` row
  with a live label was silent before 2026-11-13). **Un-choosing a job that the ledger
  owns (an earlier `reconcile --yes` installed or adopted it) makes the next `reconcile --yes` unload it**: the plan step
  reads `remove ... inventory row 'NAME' is not chosen` (only when the ledger id equals the row name and the label is not retired). A job installed by hand and never adopted is only reported.

## Reconcile and ownership ledger (S4b first write path, 2026-11-10)

`ade-sched reconcile` / `just sched-reconcile` is the ADE job write path on top of the inventory:

- **Backend:** launchd LaunchAgents, systemd user units, **and** user crontab (CI-testable with
  fakes; 2026-11-10 launchd/cron write paths). Root / `--system` units are never touched.
  **Paseo schedule create/delete** landed 2026-11-10 (S4b): orthogonal to host backends (not in
  `RECONCILE_WRITE_BACKENDS`); ledger rows use `backend="paseo"`.
- **Default dry-run**; `--yes` executes. Pending intent is written to the ownership ledger before any
  host write; committed ownership is recorded only after install/uninstall read-back.
- **Ledger:** `~/.local/state/djbclark-ade/jobs.json` (or `ADE_JOBS_STATE_DIR`), schema_version 1, with
  generation, logical id, host/user, backend, managed paths, artifact hash, and status
  (`pending` / `committed` / `pending-remove` / `failed`). Atomic replace; reconcile takes
  `reconcile.lock` beside it.
- **Install/reload** only ADE-owned expected `kind=ade-sched` rows that have `label` + `plist`.
  Unchanged healthy units (on-disk hash matches ledger **and** the timer is active when a timer is
  expected) get no reload; an inactive timer with matching files is activated. Completed oneshot
  services without a timer may stay inactive. Matching active units without a ledger row are
  adopted into the ledger without reload. Implicit `__ADE__` (no `--ade`) still refuses a linked
  worktree. A label rename keeps the old ledger identity (`prior_identity`) until that label's
  removal completes.
- **Remove** only labels recorded in the ledger as ADE-owned with removal authority
  (`committed` / `pending-remove` / legacy `installed`). Intent-only `pending` is **not** removal
  authority. Retired or dropped-from-inventory labels that are live but **not** in the ledger are
  reported only — never unloaded. Foreign/unknown owners are never unloaded. Cross-backend ledger
  removes refuse (reconcile with that backend to unload).
- **Paseo** (`kind=paseo`, ADE-owned, expected): reconcile plans create when the label is absent,
  adopts the ledger when live without ownership, skips when live+ledger match, and deletes only
  ledger-owned retired/dropped rows. Missing `--mode` or create fields (schedule, provider, cwd,
  prompt; timezone from inventory or `ADE_TIMEZONE`) blocks. Foreign/unknown paseo schedules are
  never unloaded without ledger authority. Injectable `paseo_run` (same pattern as
  `paseo_schedule_names`).
- Dependency/site services stay report-only. Host write backends are complete for S4b
  (`RECONCILE_WRITE_BACKENDS` = launchd/systemd/cron).
- Plists for `harden-check` and `keys-check` landed 2026-11-10
  (`com.djbclark.harden-check.plist` / `just harden-check-install`;
  `com.djbclark.keys-check.plist` / `just keys-check-install`).
  `update --auto` observe-only exits 5 by default (`ade-update --auto` /
  `ade-update-auto`); `--apply-checkout` / `ADE_UPDATE_AUTO_APPLY=1` ff-only
  updates **this checkout** when behind (option 1); `--apply` (options 2–3,
  operator ruling 2026-11-12) runs the scheduled apply: **mid-turn skip**
  (machine-wide `paseo ls -g --background --json`; any `running`/`initializing`
  agent defers, and an unavailable/unknown fleet reading defers too — unknown
  or busy state defers), **durable deferral** (the deferral and the
  applying-intent records are written atomically to
  `~/.local/state/djbclark-ade/update-auto.json` before any write; deferral
  exits 6), checkout fast-forward plus dependency `update_argv` with evidence
  and one doctor-driven retry per component (`ade-install update --yes`), and
  **one hermes-ping per failed run** (`ADE_UPDATE_HERMES_PING` overrides the
  tool; a missing/failing ping tool is recorded, never raised). The daily
  check job stays check-only and **no apply plist is installed or loaded by
  this repository** — installing an apply job remains an explicit operator
  step (`just update-check-install` is check-only).
- Dependency update execution (2026-11-12, unit W20): `just update` with no
  arguments runs the full S4 sequence — checkout fast-forward, then
  `ade-install update --yes` (each candidate's own `update_argv` with
  evidence; scoped doctor; one retry per doctor-failing component, reported,
  never rolled back), then doctor. See docs/install-catalog.md for the exit
  and evidence contract.

## Placeholders

Placeholders are filled into the **parsed** plist (strings inside values, never the XML text, so a value with `<` or `&`
stays a value). `__ADE__`/`@ADE@` (the checkout, realpath) and `__HOME__`/`@HOME@` are always filled; everything else
comes from `--set` (or `subst=` in the API) and wins over the defaults. Each string is filled in one pass, so a filled
value is never filled again. Any `__NAME__` or `@NAME@` left afterwards is **exit 2**. The plists in use on 2026-11-04 need:
`config/launchd/com.djbclark.deadline-sweep.plist` and `com.djbclark.pr-policy.plist`: `__STATE__` (the `@TARGET@`/`@STATE@` and
`__REPO__`/`__INDEX_DIR__` plists, proc-cpu-watch and session-history-update, were deleted in the 2026-11-06 slim-down).
`com.djbclark.ade-update-check.plist` (2026-11-09) also needs `__STATE__` for its log paths (e.g.
`--set __STATE__=$HOME/.local/state/ade`). Several plists still hard-code
`/Users/djbclark`; they parse and render as they are (later #279 slices template them).

XML comments are stripped before parsing: no plist here now (acp-dispatch-reap's, rumination-watch's and zcode-key-auth's had one; all three were deleted 2026-11-06)
would have `--` inside a comment, which XML forbids and Python's parser rejects while launchd accepts it.

**ade-sched's own plist key.** `KillMode` (`control-group`, `mixed`, `process`, `none`) sets systemd's KillMode; launchd
has no such key, and ade-sched leaves it out of the launchd copy. The API takes `kill_mode=` too.

## Detection (`--backend auto`)

1. an explicit `--backend` (or `backend=` in the API);
2. `ADE_SCHED_BACKEND` = `launchd` | `systemd` | `cron` | `none` (`none` turns scheduling off: exit 69); `auto` or empty is unset;
3. macOS (`darwin`) with `launchctl` -> launchd;
4. `/run/systemd/system` exists and `systemctl --user is-system-running` prints `running`, `degraded`, `starting` or
   `initializing` on **stdout** (the exit code is not read: `degraded` exits 1 and the manager works) -> systemd. When
   `XDG_RUNTIME_DIR` is unset (cron, ssh without pam_systemd, `sudo -u`) and `/run/user/UID/bus` exists, ade-sched sets
   `XDG_RUNTIME_DIR` and `DBUS_SESSION_BUS_ADDRESS` for its `systemctl` children first;
5. systemd is booted but the user manager does not answer -> **exit 69** with the export hint, never a silent fall back to cron;
6. no systemd and `crontab` on PATH -> cron;
7. otherwise exit 69 ("no scheduler").

## Overrides

| env | default | per-call keyword (API) |
| --- | --- | --- |
| `ADE_SCHED_LAUNCHCTL`, `ADE_SCHED_SYSTEMCTL`, `ADE_SCHED_LOGINCTL`, `ADE_SCHED_CRONTAB` | the binary on PATH | `launchctl=`, `systemctl=`, `loginctl=`, `crontab=` |
| `ADE_SCHED_LAUNCH_AGENTS` | `~/Library/LaunchAgents` | `agents_dir=` |
| `ADE_SCHED_UNIT_DIR` | `${XDG_CONFIG_HOME:-~/.config}/systemd/user` (a relative `XDG_*` counts as unset) | `unit_dir=` |
| `ADE_SCHED_LOCK` | `${XDG_STATE_HOME:-~/.local/state}/ade/ade-sched.lock` | `lock_path=` |

A keyword beats the env variable, so an installer could honour its own older override by passing it through; none does
since 2026-11-06 (the installers with older overrides, acp-dispatch's reap, context-budget-check's and skillopt-night's,
were deleted in slim-down E5, E6 and E10; `bin/deadline` and `bin/pr-policy` pass none). `tests/conftest.py` pins all seven variables (four binaries, two directories, the lock) to `/usr/bin/true` and a throwaway
directory, unconditionally, so no test touches a real launchd, systemd or crontab.

## Linger

A systemd user manager without linger starts at login and stops at the last logout, taking its timers with it: a job
would run only while someone is logged in (the "deadlines never enforced" failure in #279). Before writing anything, a
systemd install reads `loginctl show-user USER -p Linger --value`; `no` is **exit 69** with
`sudo loginctl enable-linger USER` in the message, unless `--allow-no-linger` (`allow_no_linger=True`), which installs and
prints the same warning. ade-sched never runs sudo. An unreadable value is a note, not a refusal. `ade-sched backend`
prints the state.

## Mapping

| launchd key | systemd | cron |
| --- | --- | --- |
| `ProgramArguments` / `Program` (argv[0] absolute) | `ExecStart=`, each argument double-quoted: `\`->`\\`, `"`->`\"`, `%`->`%%`, `$`->`$$` | `shlex.quote` each argument, then every `%` -> `\%` |
| `StartInterval N` | oneshot service + timer: `OnActiveSec=` (1 s with RunAtLoad, else N s), `OnUnitActiveSec=Ns`, `AccuracySec=1s` | N >= 60: the nearest evenly dividing step, rounded down with a note (`*/m` minutes, `0 */h` hours, daily); N < 60: **exit 69** ("cron cannot run every Ns; use systemd") |
| `StartCalendarInterval` (dict or list) | one `OnCalendar=` per dict, two when it has both `Day` and `Weekday` (either one matches, as in launchd and cron; 2026-11-06) (Weekday 0 and 7 = Sun; a missing field is `*`), `Persistent=true`, `AccuracySec=1s`; plus `OnActiveSec=1s` with RunAtLoad | one line per dict, fields as given (Weekday 7 -> 0) |
| `RunAtLoad` only | oneshot service, `WantedBy=default.target` | `@reboot` |
| `KeepAlive` (true, or `{SuccessfulExit: false}`) | `Type=simple`, `Restart=always` (`on-failure` for SuccessfulExit false), `RestartSec=10s`, `WantedBy=default.target` | **exit 69**: cron cannot supervise |
| `EnvironmentVariables` | `Environment="K=V"` (`%` escaped) | `/usr/bin/env K=V ...` |
| `PATH` in it (Mac paths) | `%h/.local/bin:/usr/local/bin:/usr/bin:/bin` first, then the plist's; set when absent | `$HOME/.local/bin:/usr/local/bin:/usr/bin:/bin` (filled at install) first |
| `WorkingDirectory` | `WorkingDirectory=` | `cd DIR &&` |
| `StandardOutPath` / `StandardErrorPath` | `StandardOutput=append:P` / `StandardError=append:P` (systemd 240+; 236-239 `file:`, which truncates; older: the journal, with a note); the parent dir is created | `>>P 2>&1`, or separate redirects; a missing one goes to `/dev/null` |
| `Nice`, `LowPriorityIO`, `ProcessType=Background` | `Nice=` (Background without Nice: 10), `IOSchedulingClass=idle` | ignored, with a note |
| (oneshot defaults) | `KillMode=process` (launchd leaves setsid-detached workers alive: bin/deadline's sweep starts them), `TimeoutStartSec=max(3 x StartInterval, 300 s)`; a calendar job: max(its shortest gap, capped at a day, 300 s) | — |
| any other key | kept in the launchd copy; a note on systemd and cron | |

Refused with exit 2 on every backend: a newline, CR or NUL in any argument, environment value, working directory or log
path; an `EnvironmentVariables` name matching `(?i)(KEY|TOKEN|SECRET|PASSWORD)` (a secret never goes into a unit file or
crontab; fetch it at run time with `sudo-secretspec get`); a relative program; a job with nothing to schedule (systemd, cron).

Files are written atomically (a temp file beside, then `os.replace`) with mode 0600. The crontab is never rewritten from a
bad read: `crontab -l` exit 1 with "no crontab" on stderr means empty; any other failure is exit 1 and nothing is written.
Foreign crontab lines and other labels' blocks are kept; installing twice leaves one block. A systemd install removes a
cron block of the same label; a systemd job that loses its schedule has its old timer disabled and removed.

**Worktree guard.** When `__ADE__` defaulted to the checkout ade_sched.py lives in and that checkout is a linked git
worktree (its `.git` file names a gitdir with a `commondir`), install refuses with exit 2 unless `--ade` / `ade=` is given;
dry-run and render are allowed.

## Exit codes

| code | meaning |
| --- | --- |
| 0 | done (uninstall of something not installed included); `diff` with no failing drift |
| 1 | an activation command failed (its stderr is quoted), or `crontab -l` failed for a reason other than "no crontab"; `diff`/`doctor` ADE drift (missing expected or retired still present) |
| 2 | bad job or usage: unparsable plist, unfilled placeholder, newline in a value, secret-looking env name, worktree guard |
| 3 | `status LABEL`: a named label is not installed |
| 69 | no usable scheduler: `none` forced, nothing found, systemd user manager unreachable, Linger=no without `--allow-no-linger`, KeepAlive or StartInterval < 60 s on cron |

## Admission and deferred reconciliation (2026-11-12)

`ade-sched reconcile --yes` now returns **6** for durable deferral. Existing
healthy definitions still skip reloads. Installing, reloading or removing a job
requires a shared admission
context held through read-back and the ownership commit. Its `JobAdmission`
evidence must prove all launch paths participate, per-job activity is idle,
and future triggers are safely drained. Busy/unknown jobs and the updater's own
running service defer without stopping work. A fleet idle snapshot is insufficient.
Before 2026-11-12 no native adapter existed and production deferred every install and removal; the launchd adapter below
is the first.

### Native launchd admission (2026-11-12, narrowed in rounds 2 and 3)

`ade-sched reconcile --yes` and `ade-install apply` pass `native_admission=True`. On the **launchd** backend (activation
on) that installs `launchd_admission` as the `admission` callback and routes installs through `install_launchd_native`.
An explicit `admission` argument still wins, and no environment variable or CLI flag selects or bypasses the native path.
The adapter runs one read-only `launchctl print gui/UID/LABEL`; the install path never calls `bootout`, never replaces
or unlinks a file, and never disables, enables or kickstarts anything.

**Why so little is enabled.** A live probe on macOS 27.2 (2026-11-12, throwaway label `StartInterval=5`) showed
`launchctl disable` on a *loaded* job does **not** stop its StartInterval trigger and `kickstart` still starts it. An idle
read followed by `bootout` is two operations (a trigger can start work between them), and a hash check followed by a
replace or an unlink cannot be atomic against another writer: the reconcile lock only serializes reconcilers. So native
admission enables exactly the writes that cannot kill or overwrite under concurrency, and everything else defers
(durable `jobs-deferred.json`, exit 6):

1. **Absent job** (not loaded; nothing at `agents_dir/LABEL.plist`, not even a dangling symlink): the plist is created
   exclusively (an `O_EXCL` temp file hard-linked to the target, so an existing path is never replaced) and then
   `launchctl bootstrap` runs. If the path appeared since admission, nothing is written and the step defers with the
   pending ledger intent rolled back (the log directories may already exist). If `bootstrap` fails (for example an outside loader loaded the label meanwhile) the
   step is `failed` with **no** `bootout` and no unlink: the running work survives, and the new plist stays on disk and
   is named in the failure.
2. **Unloaded job whose plist byte-matches the ADE render** (a regular file, not a symlink): `launchctl bootstrap` only,
   no write. A ledger-owned file that differs from the render is **not** overwritten (a recorded hash cannot make
   check-and-overwrite atomic): it defers untouched, as does any foreign, replaced, non-UTF-8 or non-regular file.
3. **Adoption** of a loaded job whose plist byte-matches the render stays a ledger-only record (`adopted`), with no
   `launchctl` call and no admission (nothing is mutated on the host).
4. **Loaded job, any state**: defers untouched (`parse_launchd_activity` only words the reason) **unless it is
   wrapper-routed and provably ADE's**; see "Wrapper-routed jobs (W21c)" below. A removal defers unless the same proof holds.
5. **Renames and retirements** of launchd jobs defer (exit 6) unless the old label is wrapper-routed and provably ADE's
   (then its removal runs under the lock first and the new label installs as an absent job); a removal that defers
   keeps the same logical job's new-label install deferred behind it.
6. **Label check** and **blocked rows**: a catalog `label` that differs from the plist `Label` is `blocked` at plan time
   and refused again before install. A blocked logical row (missing or unrenderable source, label mismatch) keeps its
   current and prior identities: `plan_reconcile` emits no removal for them (this protects low-level callers too).

The updater's own service (`com.djbclark.ade-update-check`) running keeps its existing refusal reason.

### Wrapper-routed jobs (W21c, 2026-11-13)

Every ADE launchd job in `config/launchd/com.djbclark.*.plist`, and (W21d, 2026-11-13) `launchd/com.djbclark.load-watch.plist`, now starts through `bin/ade-job-run --lock-dir __ADMISSION__ LABEL -- COMMAND...`
(`__ADMISSION__` is filled with the ONE canonical lock directory, `<real home>/.local/state/djbclark-ade/admission` from `pwd.getpwuid(os.getuid()).pw_dir` and never from `$HOME`, `XDG_STATE_HOME` or `ADE_JOBS_STATE_DIR` (`canonical_admission_dir`; tests inject it by monkeypatching that function); it is an argv value of the loaded job; `dev.herdr.server`, a KeepAlive server with a hard-coded path, is not migrated; see `--restart-service` below). Each run takes a **shared**,
non-blocking `flock` on `<lock dir>/LABEL.lock` and keeps it for the whole run (the lock descriptor is
inherited by the exec'd command, so it lives as long as the command; a child started with `close_fds=True` does not inherit it). If it cannot, because
reconcile holds the lock exclusively, it logs one line to the job's stderr and exits 0 without running the command (launchd
tries again on its own schedule). If the lock cannot be used for any other reason the command is not run (exit 75).

For a **loaded** job, `launchd_admission(wrapped=...)` admits a reload or a removal only when all of these hold, each read
at admission: (a) the INSTALLED plist bytes parse and route every launch through the wrapper (`ProgramArguments` is
`[<abs>/ade-job-run, "--lock-dir", <abs dir>, LABEL, "--", command...]`, an existing executable wrapper, no `Program` key; the render is not
trusted); (b) the ledger row is ADE's, `committed` (for a reload) or `committed`/`pending-remove` (for a removal), backend
launchd, with the artifact hash of those very bytes; (c) `launchctl print` says it was loaded from that plist (`path =`) **and the LOADED definition is the wrapped one**: its
`program`/`arguments` start with the same `[<ade-job-run>, --lock-dir, DIR, LABEL, --]`, and a printed `program` is required (launchd never re-reads an edited plist, so a
file written by `install --no-activate` or a failed bootstrap can show the wrapper while the old unwrapped definition runs);
(d) **the lock identity is the LOADED job's own argv** (review F1 of #622): the `--lock-dir DIR` that `launchctl print` shows for the
loaded definition must equal the directory reconcile locks (`admission_dir`); the disk plist's `EnvironmentVariables`, a domain
environment or a later edit are not proof, and a disagreement defers; (e) **the wrapper is positively identified** (review F2): the
loaded `program` resolves (`realpath`) to `<ADE root>/bin/ade-job-run` of the checkout reconcile runs from, its bytes equal that
checkout's `bin/ade-job-run`, and running it directly (no shell, 10 s timeout) with `--admission-protocol` prints `v1`
(`WRAPPER_PROTOCOL`). A stale or custom executable of that name, or a wrapper edited since the job was loaded, defers; reinstall the job to migrate it.
It then takes the label's lock **exclusive, non-blocking**: held by a run means busy, so the step defers (never wait, never
kill); acquired means no run is active and none can start. The lock stays held across the whole mutation and is released
only after the ledger commit.

Mutation order (`reload_launchd_locked`): a private copy of the prior bytes and a durable recovery record in
`<real home>/.local/state/djbclark-ade/admission/` (the canonical lock directory), then `bootout` (with proof it unloaded; if not, nothing changed and the step defers), the new
bytes by atomic replace, `bootstrap`, read-back. A failure after the unload restores and bootstraps the **prior** bytes
(`ReloadRolledBack`: the ledger keeps the old committed row and the run exits 1), or, if that also fails, keeps the record
and exits 1. A SIGTERM, deadline kill or crash cannot run any cleanup, so the record is the guarantee: every `reconcile`
first acts on records (`recover_launchd_records`; `--dry-run` lists them as `would-recover`): a loaded label clears a stale
record; an unloaded label whose plist is still the prior (or the new) bytes is bootstrapped and its ledger row made
committed for what is loaded; recovery acts only on a label some ADE launchd ledger row names; a plist that is neither is someone else's and is left alone (row `failed`, record kept).
The lock is released only after the ledger commit, so the new definition's `RunAtLoad` run skips (exit 0) and the next run is at its `StartInterval`. A restore never overwrites a file that is neither the prior bytes nor the bytes this run wrote. A removal interrupted after the unlink (no plist, unloaded, ADE `pending-remove` row) is completed by the next run (the ledger row is dropped). Every ADE job now imports `ade_sched.py` from the shared checkout, so a broken checkout stops all of them (exit 1 or 127, not 75).
**ADE writers serialize (review F3).** `install` and `uninstall` (launchd), `install_launchd_native`, the locked reload and removal and the recovery restore all take the label's admission lock **exclusive, non-blocking** around their check-and-write (`writer_lock`): a run in flight or another ADE writer makes them refuse (`SchedError` / `NativeDefer`, nothing written, no `bootout`). Under the lock every replace, unlink and restore re-reads the plist through one descriptor immediately before the syscall and compares its inode (`st_dev`/`st_ino`) and sha256 with the ones it hashed (`_guarded_replace`, `_guarded_unlink`): another inode or other bytes raise `ForeignWrite` and nothing is replaced or deleted. The `com.djbclark.ade-*` / ADE-catalog label namespace under `~/Library/LaunchAgents` is **reserved to ADE**: a non-ADE process writing there is outside the contract, and the residual window is the gap between that last read and the `rename`/`unlink` (and between our write and launchd's read of it). The `admission/` directory is never cleaned while jobs run: unlinking a held `LABEL.lock` lets reconcile lock a new inode and unload a live run. A recovery record that no ADE ledger row owns (or an unreadable one) fails every `--yes` run and every `--dry-run` until it is discarded by hand: delete `<real home>/.local/state/djbclark-ade/admission/LABEL.recovery.json` and `LABEL.prior.plist` (the environment does not move that directory); `ade-sched uninstall` of a label discards its record itself. **One lock identity (review F4).** The wrapper's rendered `--lock-dir`, reconcile, recovery and every low-level writer use `canonical_admission_dir()`; the caller's environment cannot move it, so two ADE writers can never lock one label in two places. Before any bootout, replace or unlink of a LOADED label, `ade-sched install`/`uninstall` also prove from `launchctl print` that the loaded job runs `ade-job-run --lock-dir <canonical> LABEL --` (the wrapper's realpath is `<ADE root>/bin/ade-job-run`, where the root is the explicitly selected `--ade` or else the checkout holding the running `ade_sched.py`, never unbound; this checkout's wrapper bytes; protocol v1) and refuse without writing otherwise (exit 1, naming `migrate-wrapper`; the one exception is `--restart-service`, below). A LOADED, canonical job that is reinstalled goes through the same record-first reload as reconcile (prior copy, recovery record, restore on failure), and a new definition that would leave the wrapper is refused. `__ADMISSION__` cannot be set (`--set`, a catalog `set` row, `extra_subst`). A removal of an unloaded label re-asks launchd under the lock and defers if it was loaded meanwhile. Removal (`remove_launchd_locked`) re-hashes the file under the lock right before the unload, uses the same record while
the job is loaded, and restores it if the unlink or read-back fails.

**A job not routed through the wrapper keeps #619's deferral, so every existing install defers (exit 6) until it is
migrated once, and low-level `install`/`uninstall` refuse it (exit 1).** Migration is the operator's call, at a quiet time:
`bin/ade-sched migrate-wrapper PLIST [--ade DIR] [--set K=V]` (`migrate_wrapper_launchd`). It takes the canonical lock exclusive,
refuses while `launchctl print` shows a pid or any state but `not running` (nothing changed), refuses a job that already runs
through the canonical wrapper (use `install` or reconcile), then writes the recovery record, boots out, writes the new
render, bootstraps and reads back; a failure restores the prior bytes. After it, reconcile adopts the file as the
ledger's artifact and reloads it normally. **The old lock too (B7, W21d).** When the OLD loaded definition is itself a wrapped job
(`ade-job-run --lock-dir DIR LABEL`) whose `DIR` is not the canonical directory (a different spelling of the same directory, by
`realpath`, does not count), `migrate-wrapper` also takes `DIR/LABEL.lock` **exclusive and non-blocking** for the whole migration and
releases it in a `finally`: a run of the old wrapper holds that lock shared, so a busy lock refuses the migration with nothing changed
and no `bootout`; a `DIR` that does not exist holds no lock and is never created (only the idle check applies). A pre-wrapper (unwrapped) old definition has no lock to take, so its one risk stays: a run of the OLD definition
that starts between the idle read and the bootout is not seen, so pick a quiet time.

`migrate-wrapper` refuses a new render that does not itself route through the canonical wrapper. **`com.djbclark.load-watch` is wrapped
since W21d (2026-11-13)**: `launchd/com.djbclark.load-watch.plist` starts `bin/load-watch sample` through `ade-job-run` like the nine catalog plists, so
once an install is migrated (`bin/ade-sched migrate-wrapper launchd/com.djbclark.load-watch.plist --ade DIR`, once, at a quiet time; the
sampler runs every 20 s and holds the shared lock only while a sample runs) `load-watch install` and `load-watch uninstall` work on the
LOADED job through the locked record-first path above. Because every sample now goes through the wrapper, load-watch needs the shared checkout's
`ade_sched.py` (the wrapper imports it) and a lockable canonical `admission/` directory on every sample: a broken `ade_sched.py` or an unusable lock
directory (wrapper exit 75, not contention) silently stops the sampler too, the watchdog that would have reported it. An install made before W21d is a pre-wrapper job and `load-watch install`/`uninstall`
refuse it (exit 1, naming `migrate-wrapper`) until it is migrated. Jobs that are not wrapped by design (`dev.herdr.server`, any non-catalog plist)
cannot be installed or uninstalled by `ade-sched` while LOADED, with one exception.

**`--restart-service` (W21d, 2026-11-13): a deliberate service restart, not paid-work-safe.** `ade-sched install PLIST --restart-service` and
`ade-sched uninstall LABEL --restart-service` (low-level `install(..., restart_service=True)` / `uninstall(..., restart_service=True)`; launchd only)
are the ONLY way to replace or remove a LOADED job whose loaded definition is not canonical-wrapped, and only for a KeepAlive service that is
NOT running through `ade-job-run`. The LOADED side must prove it (`_restart_service_problem`, review F1-F4 of W21d): the loaded program is not an
`ade-job-run` (any wrapper-shaped loaded argv whose lock identity is not the canonical one is refused outright, because its runs may hold another
directory's lock: use `migrate-wrapper`), and the INSTALLED file (read once as bytes, parsed with `plistlib`) is regular, has this Label and no `Program` key,
its `ProgramArguments` equal the `arguments` that `launchctl print` shows for the loaded job with `program == arguments[0]` (launchd never re-reads an
edited file, so the file's `KeepAlive` counts only when the file provably IS the loaded definition; `launchctl print` does not show KeepAlive, so a
KeepAlive-only edit of an otherwise identical file is an undetectable limit), and its `KeepAlive` is truthy. An install additionally requires the NEW
definition's `KeepAlive` to be truthy (both sides, never only the new one). The remove/replace re-hashes exactly the bytes that were checked. Without the
flag, and for any job that fails these proofs even with it, the command refuses exactly as before (exit 1, nothing written). With it the `bootout` WILL stop the running service: nothing
protects its in-flight work, so use it only for a service whose restart is acceptable. The safety it keeps: the label's canonical lock is
held exclusive without waiting (a busy lock still refuses, the flag never bypasses it), the durable recovery record and the prior-bytes
copy are written BEFORE the `bootout`, the `bootout` is proven (the label must be unloaded), the new definition is bootstrapped and read back
(an install) or the file removed and read back (an uninstall), and a failure puts the prior bytes back and bootstraps them (`ReloadRolledBack`);
if that restore also fails the recovery record and the prior copy stay in `admission/` and the error says so, **and the service stays DOWN**: for a label
with no ADE ledger row (a non-catalog KeepAlive service such as `dev.herdr.server`) `recover_launchd_records` never acts on the record (it reports
`failed`, which fails every `reconcile` run and `--dry-run` until the record is discarded), so load it by hand as the error message prints: copy
`<real home>/.local/state/djbclark-ade/admission/LABEL.prior.plist` to `~/Library/LaunchAgents/LABEL.plist`, run `launchctl bootstrap gui/UID` on it, and delete the
`LABEL.recovery.json` and `LABEL.prior.plist` files.
The flag has no effect on a canonical-wrapped loaded job (it takes the normal path, and a new definition that leaves the wrapper is still refused) nor on
systemd and cron; `--no-activate` is refused (exit 2) only when the flag would restart a loaded job (a restart is a bootout), and is otherwise unaffected. `load-watch` itself does not forward the flag: its job is a StartInterval
sampler, never a KeepAlive service.

**The one deliberate exception to admission: load-watch's emergency stop (B9, W21d).** The job guard (`bin/load-watch`, `guard_stop`,
`guard_restart`, `guard reset`) exists to stop a runaway job NOW: it runs `launchctl bootout`, `launchctl disable` (the 5th round in 24 h) and
`kill -TERM` then `-KILL` of the job's processes, and later `launchctl bootstrap`/`enable` of the job's plist, without taking the admission
lock, without a recovery record, and without regard for work in flight. Making it wait for the no-kill lock would defeat its purpose, so it is
the one place where the no-kill contract above does not apply; "every ADE lifecycle writer takes the admission lock" is therefore false for
the guard, and no universal all-ADE-process no-kill or recovery guarantee covers a guarded label. It only acts on a job that crash-loops (any
non-Apple job) or trips a limit of `~/.config/load-watch/guard.tsv`; cooldown state is kept in `state.json` in memory-first order (set before the bootout, event
after), not in the scheduler's record-first protocol. How it meets the scheduler: (a) a **cooled-down** job is booted out and its plist stays, so `reconcile --yes`
sees an unloaded job whose plist byte-matches the render and may `bootstrap` it again (the native install path: it takes the exclusive writer lock, but needs no loaded-job admission for an unloaded
job), before the guard's own `guard_restart` re-test, which then finds it loaded ("already loaded by someone else; watching it"); a `disable`d job
(the permanent stop) makes that bootstrap fail, the ledger row `failed`, and stays off until `load-watch guard reset LABEL`. (b) A guard
`bootout` or kill that lands DURING a locked reload or removal makes that operation take its failure path: the read-back or bootstrap fails, the prior
definition is restored and bootstrapped (`ReloadRolledBack`, exit 1), or, if the restore fails too, the recovery record stays and the next reconcile acts on
it (`recover_launchd_records`); the guard's own state and the scheduler's then disagree until `guard reset`. Coordinate a deliberate restart
of a guarded label with the guard (`load-watch guard rm LABEL` first, or wait for the cooldown) rather than racing it.

Not covered by the lock: a run launchd has spawned whose wrapper has not yet taken the shared lock when reconcile takes it
(the wrapper has done no work, so the unload loses none); a writer that changes the plist between our byte-match and the
write or unlink (the guarded re-read and inode check detect it except for the syscall gap);
and a job that is not an ADE job. **Known limits:** a concurrent external loader can still bootstrap an absent or
unloaded job (this path then fails or defers and never boots it out); another writer that changes an unloaded file between
the byte-match read and `bootstrap` gets its definition loaded (nothing is overwritten); an operator-disabled
(`launchctl disable`), unloaded ADE job is admitted, its `bootstrap` fails and the ledger row becomes `failed`; and, a limit that
stays latent until removals are ever admitted, adoption does not compare the loaded job's `path =` with our plist, so a job an
outside loader loaded can be adopted ledger-only when a matching file sits at the path (any removal follow-up must require
a regular-file plist and a `print` `path =` equal to it); the live backend scan (`list_backend_labels`, `installed_labels`, and reconcile's own byte-match reads; fixed 2026-11-13)
never opens a non-regular `*.plist`/`*.service` entry: it `lstat`s first, opens regular files `O_NONBLOCK|O_NOCTTY`
(`O_NOFOLLOW` unless the entry is a symlink to a regular file), re-checks with `fstat`, and reads a bounded amount. A FIFO,
device, socket, directory or symlink to one is listed with source `non-regular`: it is no live identity (`LiveScan.ids`
omits it, so a missing job is still reported missing) and `scan_live` adds one note per entry, which `reconcile` and `diff`
print as a report line; nothing is ever unloaded for it.

**systemd, cron and paseo keep the conservative default** (installs and removals defer, exit 6): no adapter proves their
launch paths yet. A paseo step on a launchd host also keeps it, and so does `--no-activate` (the adapter needs `launchctl`).
Direct low-level `install`/`uninstall` are outside this contract; callers must not treat those paths as proof of global
admission.

**Adoption.** A job installed with low-level `ade-sched install` whose files match the ADE render and which is loaded is
recorded in the ledger by `reconcile --yes` as `adopted`, without a reload and without admission (nothing is mutated on the
host). A job whose files differ from the render is an install/reload step and goes through the adapter.

Deferral intent is atomically stored in `jobs-deferred.json` beside `jobs.json`,
under the existing reconciliation lock, with logical ID, action, backend, label,
reason and prior identity. Paseo intents use backend `paseo` regardless of the
host backend selected, so retries update one logical intent. It confers no
removal authority. Retries retain intent;
a successfully reconciled logical job clears its resolved deferral. Dry-run writes
no deferral record. `ade-install apply` propagates scheduler exit 6 when no other
component fails. Component-ledger serialization and scheduled updater policy are
separate contracts.

Backend migration of an existing logical ID defers before adoption, installation
or removal, including same-label changes. The old ownership record stays intact.
Automatic migration remains unavailable until an old-backend adapter can drain,
verify absence (distinguishing unknown from absent), and only then install the
new backend. No fallback to cron is introduced for unavailable user managers.
