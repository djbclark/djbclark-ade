# Prior art: reproducible, synchronized personal AI coding-agent environment (2026-10-19)

Scope note: evidence is from web search snippets and docs; I did not run anything. Inference is labelled INFERENCE. Mycelial and Perkeep: no useful 2025-26 evidence found.

## 1. Syncing Claude Code state

1.1 Transcripts live at ~/.claude/projects/<cwd, non-alphanumerics replaced by "-">/<session-id>.jsonl; names over 200 chars are truncated plus hashed. Entry format is internal and changes between versions. — https://code.claude.com/docs/en/sessions
1.2 Relocation knobs: CLAUDE_CONFIG_DIR (move whole tree), CLAUDE_CODE_PROJECT_DIR_NAME (v2.1.234+, pins the project dir name, only honoured with CLAUDE_CONFIG_DIR, must come from the shell env not settings.json), cleanupPeriodDays (30-day default). — https://code.claude.com/docs/en/sessions
1.3 Official guidance on multi-machine sync is absent: nothing is shared between computers; the supported cross-machine routes are cloud sessions/teleport and the Agent SDK SessionStore (dual-write mirror with append/load; S3, Redis, Postgres reference adapters; transcripts only, best-effort). — https://code.claude.com/docs/en/agent-sdk/session-storage , https://code.claude.com/docs/en/claude-code-on-the-web , https://codonic.dev/guides/move-claude-code-session-to-another-computer
1.4 Moving a session by hand: copy the .jsonl (plus the same-id side folder and ~/.claude/file-history) into the project dir that matches the NEW machine's checkout path. Transcripts embed absolute paths, so differing username or layout needs a careful path rewrite (prefix collisions, JSON-escaped Windows paths, signed thinking blocks). — https://codonic.dev/guides/move-claude-code-session-to-another-computer
1.5 Resume pitfalls: since v2.1.223 `--resume <id>` searches all projects but only if exactly one project holds that id; a duplicate copy makes it report not-found. Resume fails if the original cwd is gone (recreating an empty dir fixes it). Worktree/devcontainer path keys diverge between session writer and /resume. cp -p/rsync -a keep old mtimes, so the 30-day sweep can delete a fresh copy. — https://code.claude.com/docs/en/sessions , https://github.com/anthropics/claude-code/issues/57920 , https://github.com/anthropics/claude-code/issues/33665
1.6 Plugins: declarative state is settings.json `enabledPlugins` + `extraKnownMarketplaces`; fetched state (installed_plugins.json, known_marketplaces.json, cache/) holds absolute installPath/installLocation and is machine-specific; project-scope enablement does not auto-install. Sync the settings keys, not the plugin cache. — https://code.claude.com/docs/en/plugins/loading , https://code.claude.com/docs/en/plugins/install , https://github.com/anthropics/claude-code/issues/36575
1.7 Community tools (all git-based, small, unproven at scale): claude-nomad, claudefy, clync (UUID-tree merge, LFS), claude-code-sync variants, ai-sync. Typical split: sync settings.json, CLAUDE.md, skills, agents, commands, hooks; exclude caches, credentials, plugin install records. — https://github.com/funkadelic/claude-nomad/ , https://github.com/kodrunhq/claudefy , https://github.com/Saturate/clync , https://github.com/berlinguyinca/ai-sync/ , https://nickang.com/how-to-sync-claude-code-global-files-across-machines-if-you-work-on-multiple-computers/
1.8 Profile-style multi-CLAUDE_CONFIG_DIR setups hit "corrupted installLocation" when plugins/ is symlink-shared; fix is per-profile known_marketplaces.json plus mirrored enabledPlugins. — https://github.com/daymade/claude-code-skills/blob/main/daymade-claude-code/claude-switch-models-setup/scripts/claude-plugins-sync.py

## 2. Other TUIs: storage and sync/export

2.1 Codex CLI: rollout jsonl files under ~/.codex/sessions/YYYY/MM/DD plus session_index.jsonl; copying a rollout file to another machine and resuming works per community guides; no official sync. — https://spawnd.dev/codex-cli-sessions , https://www.zonca.dev/posts/2025-12-16-copy-codex-session , https://github.com/Red-noblue/Codex_Relay
2.2 OpenCode: sessions in a SQLite DB (opencode.db) under its data dir; has `opencode export` / `import` commands (JSON), the supported portable path. — https://opencode.ai/docs/cli/ , https://opencode.ai/docs/troubleshooting/
2.3 Gemini CLI: per-project-hash chat/checkpoint dirs under ~/.gemini; project hash derives from path, so same path-dependence as Claude. — https://geminicli.com/docs/cli/session-management/ , https://google-gemini.github.io/gemini-cli/docs/cli/checkpointing.html
2.4 Copilot CLI: ~/.copilot session-state files plus session-store.db; `--remote-export` exists in the command reference. — https://docs.github.com/en/copilot/reference/copilot-cli-reference/cli-config-dir-reference , https://docs.github.com/en/copilot/reference/copilot-cli-reference/cli-command-reference
2.5 Cursor: state.vscdb / store.db SQLite plus transcripts; only third-party exporters (cursor-history, cursor-session); no sync. — https://github.com/S2thend/cursor-history , https://github.com/iksnae/cursor-session
2.6 Summary (INFERENCE from 2.1-2.5): no vendor offers cross-machine local session sync; the common denominator is "jsonl per session (Claude, Codex)" versus "SQLite (OpenCode, Copilot index, Cursor)". Treat jsonl as syncable files and SQLite as export/import or replicate-by-tool.

## 3. SQLite replication options

3.1 Litestream: streams WAL to object storage/SFTP for backup and restore; one writer, replica is read-only/restore target, not multi-writer sync. — https://litestream.io/how-it-works/ , https://litestream.io/tips/
3.2 LiteFS: Fly.io's FUSE/primary-lease replication; Cloud discontinued and community threads treat the project as unmaintained. Avoid. — https://community.fly.io/t/litefs-discontinued/23682 , https://fly.io/blog/litefs-cloud/
3.3 cr-sqlite: CRDT column-wise LWW multi-writer merge; upstream maintenance is thin (open issues), a maintained successor in this style is sqliteai/sqlite-sync. SQLSync is similar in spirit but research-grade. — https://github.com/vlcn-io/cr-sqlite/ , https://github.com/vlcn-io/cr-sqlite/issues/444 , https://github.com/sqliteai/sqlite-sync , https://sqlsync.dev/posts/stop-syncing-everything/
3.4 Turso/libSQL sync: local-first push/pull against a Turso Cloud database with configurable conflict handling; needs a Turso server, not just git. — https://docs.turso.tech/sync/usage , https://docs.turso.tech/sync/conflict-resolution
3.5 Dolt: version-controlled SQL; since Feb-Mar 2026 supports plain Git remotes and SSH remotes, so GitHub/Forgejo can be the remote. Best fit for "SQL + only git hosts", but it is a different engine, not a SQLite replicator. — https://www.dolthub.com/blog/2026-02-13-announcing-git-remote-support-in-dolt/ , https://www.dolthub.com/blog/2026-03-17-announcing-ssh-remotes/ , https://www.dolthub.com/docs/concepts/dolt/git/remotes/
3.6 rqlite is Raft: needs a live quorum of servers, wrong shape for laptops that sleep. (General knowledge, not freshly sourced.) Mycelial: no 2025-26 evidence found, treat as unavailable.
3.7 File-level sync (Syncthing, Dropbox, iCloud) of a live SQLite DB is unsafe: WAL/SHM multi-file state, mmap, mtime games, conflict copies; SQLite's own corruption guide lists naive copying as a hazard. — https://www.sqlite.org/howtocorrupt.html , https://forum.syncthing.net/t/sync-conflict-with-1-specific-sqlite-file-constantly/20836 , https://forum.syncthing.net/t/bahaviour-of-st-on-sqlite-files-in-various-scenarios/5921
3.8 INFERENCE: for agent state, SQLite is usually a derived index (session search, memory). Rebuild per machine from synced source files rather than replicate the DB.

## 4. Dotfile and environment managers

4.1 chezmoi: git repo as source, per-machine config from `.chezmoi.toml.tmpl` with `promptStringOnce`, templates, age/SOPS/password-manager secrets, `chezmoi init --apply <repo>` one-liner bootstrap, run_ scripts, externals. Lowest-friction for cross-OS (Mac+Linux). — https://www.chezmoi.io/user-guide/setup/ , https://chezmoi.io/comparison-table/
4.2 nix-darwin + home-manager: whole stack pinned by a flake; `darwin-rebuild switch` on Mac, `home-manager switch` on Linux; GUI apps still need Homebrew casks (declarative via nix-darwin `homebrew.*`, `cleanup = "zap"`; nix-homebrew pins Homebrew itself). Strongest reproducibility, highest learning/maintenance cost. — https://mattmichie.com/2026/02/14/nixifying-my-dotfiles/ , https://github.com/zhaofengli/nix-homebrew , https://gitlab.com/frankper/the-one-nix/-/blob/main/readme/manage-mac.md
4.3 Nix installer choice matters: Determinate Nix works with nix-darwin via `nix.enable = false`; Lix lacks `fetchClosure`, which breaks devbox. — https://determinate.systems/blog/nix-darwin-updates/ , https://gitlab.com/frankper/the-one-nix/-/blob/main/readme/manage-mac.md
4.4 Ansible: agentless, good for imperative provisioning (packages, services, launchd) and for gluing chezmoi plus secrets; a real example bootstraps chezmoi + age key from 1Password via an Ansible collection. — https://github.com/shanemcd/dotfiles , https://botmonster.com/self-hosting/automate-linux-desktop-setup-with-ansible-and-dotfiles/
4.5 mise (runtimes + tasks), devbox (Nix-backed per-project shells), Brewfile (macOS packages): complementary layers, not whole-environment managers. Common pattern is Brewfile or nix-darwin for packages, mise for language runtimes, chezmoi for files. — https://seds.nl/notes/my-journey-in-managing-dotfiles/ , https://github.com/bgub/nix-macos-starter
4.6 yadm: bare-git-repo approach with alternate files and encryption; simpler but weaker templating/secret story than chezmoi. — https://dotfiles.pro/alternatives , https://chezmoi.io/comparison-table/
4.7 INFERENCE: for a mixed Mac/Linux fleet with existing Ansible, chezmoi (files) + Ansible (system) + mise (runtimes) is the lowest-risk stack; Nix is the "full pin" option if you accept the cost.

## 5. Private overlay patterns (public repo + private data)

5.1 Companion-repo overlay with precedence: public repo's installer symlinks files from optional ~/.private (and ~/.corp) clones; later layers win; per-overlay `update` hooks; repo "works fine without them". Closest match to the "public base + private overlay" requirement. — https://github.com/ithinkihaveacat/dotfiles/
5.2 Fork-and-create-private explicit instructions: romkatv's dotfiles-public tells the user to fork the public repo, then create an empty private `dotfiles-private` repo that the install scripts pull. Pattern exists, but manual, not prompted. — https://github.com/romkatv/dotfiles-public
5.3 chezmoi prompting: `.chezmoi.toml.tmpl` with `promptStringOnce` asks once per machine (e.g. private repo URL, email). Combined with an `include`/external or a `run_once_` script that clones the private repo, this gives "prompted to create/point to your own private repo". Chezmoi does not itself create GitHub repos; do that with `gh repo create --private` in a run_ script. — https://www.chezmoi.io/user-guide/setup/ , https://chezmoi.io/user-guide/include-files-from-elsewhere/ , https://github.com/terrylica/cc-skills/blob/HEAD/plugins/dotfiles-tools/skills/chezmoi-workflows/references/setup.md
5.4 Encrypted private submodule: public dotfiles plus a private git submodule of age-encrypted files, key kept in 1Password, decrypted via `.chezmoi.toml.tmpl`, falls back to placeholders if the key is missing. — https://github.com/shanemcd/dotfiles
5.5 Nix: public flake plus a private flake input (fine-grained read-only PAT in nix access-tokens), or nested git+file secrets flake; sops-nix/agenix encrypt secrets at rest but cannot be used at eval time and land in the world-readable store. — https://sighery.com/posts/nixos-secrets-private-flake/ , https://simonshine.dk/articles/managing-secrets-privately-with-sops-nix/ , https://discourse.nixos.org/t/public-reusable-flake-with-private-parts/73049
5.6 Secret-manager-first alternative: nothing private in git, secrets from 1Password/Bitwarden at apply time (chezmoi onepasswordRead). — https://dotfiles.io/en/guides/secret-management/
5.7 INFERENCE (best for "fork my public repo, be prompted for own private repo"): a thin public repo with a documented overlay contract (directory layout plus precedence like 5.1), a bootstrap that asks for the private repo URL once (5.3), offers `gh repo create --private` if it does not exist, and runs identically with the overlay absent. No source found that ships exactly this end to end.

## 6. Distributed sync of append-only jsonl logs

6.1 Syncthing is fine for jsonl if each file has exactly one writer at a time; trouble comes from the same file edited on two machines (conflict copies) and from SQLite files. Config options (ignore patterns, versioning, fsWatcher) are documented. — https://docs.syncthing.net/users/config.html , https://forum.syncthing.net/t/syncing-database-with-minimal-data-delivery/17008
6.2 INFERENCE: Claude/Codex session files are unique-per-session UUID names, append-only, so conflicts only arise if the same session is resumed on two machines concurrently. That is the real risk; mitigate with a per-host subdirectory or a "resume only after sync settled" rule.
6.3 Git for jsonl: works for append-only text (clync uses UUID-tree merge and LFS), but history bloats and commit churn on active files is noisy; better as periodic snapshot or push-on-exit than live sync. — https://github.com/Saturate/clync , https://github.com/tobixen/syncthing-git
6.4 git-annex: location tracking, partial checkouts, special remotes (rsync, S3, SFTP, rclone, git-lfs); explicitly "not a folder mirroring system like syncthing", dislikes syncing .git dirs. Suits cold archive of old sessions, not live sync. — https://git-annex.branchable.com/not/ , https://git-annex.branchable.com/special_remotes/
6.5 Mutagen: two-way low-latency sync over SSH with conflict policies and ignore rules; a good fit for dev-box-to-laptop live mirroring. — https://mutagen.io/documentation/synchronization
6.6 Tailscale Taildrive is WebDAV sharing, still alpha as of Jan 2026 validation, with open Windows publication bugs; it is a remote mount, not sync. A native Tailscale sync feature is only a feature request. — https://tailscale.com/docs/features/taildrive , https://github.com/tailscale/tailscale/issues/13912 , https://github.com/tailscale/tailscale/issues/17865
6.7 rsync/rclone over Tailscale SSH: one-way, no conflict detection (rsync has none); fine for per-host append-only collection into a hub box. — https://en.wikipedia.org/wiki/Comparison_of_file_synchronization_software
6.8 Perkeep: no relevant 2025-26 evidence found; not recommended.

## 7. Cross-TUI session search and agent memory

7.1 Cross-agent session search tools (derived indexes, local): coding_agent_session_search (cass), sesh, ccrider, chat-recall, fast-resume-plus, AllSessions, sessionwiki, ai-sessions-mcp. They index Claude, Codex, Gemini, OpenCode etc. and rebuild locally; none sync across machines themselves. — https://github.com/Dicklesworthstone/coding_agent_session_search , https://github.com/ddarmon/sesh , https://github.com/neilberkman/ccrider , https://github.com/munhq/chat-recall , https://github.com/ServiceCraze/ai-sessions-mcp
7.2 Orca ships `orca search` over indexed agent transcripts, including connected computers and paired servers when hosts grant access. — https://www.onorca.dev/docs/cli/reference
7.3 Basic Memory: markdown files plus a SQLite index, MCP interface; markdown is git-syncable, the index is rebuildable. — https://github.com/basicmachines-co/basic-memory
7.4 Memory comparisons: Mem0 (vector DB), Hindsight (Postgres), Basic Memory (files); central-store systems solve multi-machine by being server-side, file-based ones by git. — https://techcoherence.com/blog/choosing-a-memory-system-for-your-ai-agent-basic-memory-vs-mem0-vs-hindsight , https://tomrochette.com/agents/memory-feature-matrix/ , https://mnemoverse.com/docs/library/memory-mcp-servers-compared
7.5 sqlite-sync offers CRDT block-LWW for markdown-in-SQLite, a possible multi-writer memory path but needs evaluation. — https://github.com/sqliteai/sqlite-sync
7.6 INFERENCE: sync source files (jsonl, markdown), rebuild per-machine indexes. A hub index on the small self-hosted box can answer cross-machine search without replicating SQLite.

## 8. Paseo

8.1 Paseo: open-source (getpaseo/paseo) daemon plus clients (desktop, mobile, CLI) that drives coding-agent CLIs; clients reach a daemon over SSH, a relay, or Tailscale/direct. — https://paseo.sh/ , https://paseo.sh/docs/connectivity , https://github.com/getpaseo/paseo
8.2 Plugin model: plugins and custom providers documented (plugin reference, providers, custom-providers), plus a configuration file. — https://paseo.sh/docs/plugins/reference , https://paseo.sh/docs/plugins/providers , https://paseo.sh/docs/custom-providers , https://paseo.sh/docs/configuration
8.3 Session persistence relies on the underlying provider CLIs' own stores; I found no evidence that Paseo syncs sessions between daemons (INFERENCE: it connects clients to one daemon per host, the daemon is the source of truth for that machine). — https://paseo.sh/llms.txt
8.4 Orca (Stably): worktree-native ADE; four run modes (local, SSH worktrees, Remote Orca Server via desktop app or `orca serve` over Tailscale, cloud VM); server owns worktrees, terminals and agent sessions; beta; `orca serve service install` writes launchd/systemd unit. — https://www.onorca.dev/docs/ways-to-run , https://www.onorca.dev/docs/remote-servers , https://github.com/stablyai/orca/
8.5 herdr: persistent terminal multiplexer for agents with an automation interface; lighter than Orca/Paseo, no worktree model. — https://herdr.dev/ , https://herdr.dev/docs/agent-automation/ , https://github.com/herdrdev/herdr
8.6 Comparison pages exist but I only skimmed them; treat feature tables as vendor-written. — https://github.com/getpaseo/paseo/blob/main/public-docs/alternatives/opencode-desktop.md , https://nimbalyst.com/blog/open-source-agent-workspace-alternatives-2026/ , https://github.com/botiverse/oar/blob/main/docs/prior-arts/feature-comparison.md
8.7 Common to all three: they place the runtime on one chosen host and attach clients to it (remote-runtime model). None reproduces or syncs environments across machines; that stays a dotfiles/git problem.

## Recommendations the evidence supports

R1 Sync source files, rebuild indexes: git or Syncthing for jsonl and markdown, never for live SQLite (3.7, 3.8, 6.1).
R2 Claude Code: sync settings.json (incl. enabledPlugins/extraKnownMarketplaces), CLAUDE.md, skills, agents, commands; do not sync plugin cache or installed_plugins.json (1.6).
R3 Transcripts: collect per-host into a hub (rsync/Mutagen over Tailscale or git snapshot), keep unique copies per session id, avoid resuming one session on two machines (1.5, 6.2). Prefer same checkout paths on every machine to avoid path rewriting (1.4).
R4 Dotfiles layer: chezmoi, optionally with Ansible for system provisioning and mise for runtimes; Nix only if full pinning is worth the cost (4.7).
R5 Public/private split: public repo with overlay contract plus chezmoi `promptStringOnce` for the private repo URL and `gh repo create --private` bootstrap (5.7); private repo holds age-encrypted secrets, key from a password manager (5.4).
R6 Do not adopt LiteFS, cr-sqlite upstream or Taildrive as foundations (3.2, 3.3, 6.6); consider Dolt only if a git-hosted SQL store is wanted (3.5).
R7 Evidence is thin on: an off-the-shelf "public fork plus prompted private repo" tool, Paseo cross-daemon sync, Mycelial, Perkeep. DECIDED: report these as gaps rather than guess.
