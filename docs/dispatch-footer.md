## Delivery contract (shared footer; leads paste it into Agent-tool / `paseo run` briefs; `agent_footer_gate` fills it inline)

The `acp-dispatch footer` helper left with the Wave 6 shim deletion (2026-11-14, [docs/slim/wave6-follow-up.md](slim/wave6-follow-up.md)); `bin/ade-worker-run` appends a one-line pointer to this file to the brief. `agent_footer_gate` fills `{report}`, `{lead}`, `{done}`, `{inbox}` and `{replies}` inline for Agent-tool prompts; new `paseo run` briefs fill them themselves, and `bin/ade-worker-run` always appends a `Footer values:` line after the pointer (or after the brief's own footer text when it names this file) that fills `{lead}`, `{report}`, `{done}`, `{inbox}` and `{replies}`. A report path the brief labels (`Report:` / `Report path:` / `Report file:`, a `## Report path` heading, "write your report to <path>", `{report} = <path>`) is used as `{report}` (its `.done` as `{done}`, unless the brief labels a `Done:` path); a path only mentioned as an input is not a label. Otherwise the tool generates `~/.local/state/agent-reports/<lead id>/<slice>-report.md` (`<slice>-N-report.md` when that name or its `.done` exists) with its `.done`, `.inbox.md`, `.replies.md`. The chosen paths go to stderr and its JSON (`reportPath`, `donePath`). A sub-agent type that cannot write files (the built-ins Explore, Plan and web-fetch, or an agent definition whose `tools:` lists neither Write nor Bash) cannot follow this contract: it gets [dispatch-footer-readonly.md](dispatch-footer-readonly.md) instead (its final message is the report, no `.done`).


1. Write the full deliverable to `{report}`. Create it early with `STATUS: working` as its first line and update it as you go; finish it **before** any optional verification. Nothing else counts as delivered.
2. Your final message is only `written: {report}` plus one sentence. The harness cuts a sub-agent's final message at 4,000 characters and the parent never sees the rest, so never put the deliverable there.
3. If the parent must read more than about 2,000 characters of it, also send the text to `{lead}` with SendMessage (an Agent-tool sub-agent's parent is `main`; `team-lead` only inside an agent team), in ordered chunks under 3,500 characters each (`1/3`, `2/3`, ...). That path arrives whole.
4. Keep the report path exactly as given. Claude Code refuses a sub-agent's Write when the basename starts with `report`, `summary`, `findings` or `analysis` and ends in `.md`.
5. Never end your turn waiting for a background task's completion notice: it does not wake a sub-agent (it is delivered only with the next inbound message, so you stall until someone writes to you). The "start slow commands in the background" rule is for interactive sessions and the lead, not for you. Hold the wait in foreground Bash calls, each bounded under the tool timeout and repeated until done (`~/src/djbclark-ade/bin/wait-file --timeout 1500 /ABS/FILE`, rule 13; `while kill -0 <pid>; do sleep 10; done`), or do independent work and check again before you end. Rule 20 limits which waits are allowed at all, and CI is never one of them.
6. Never end your turn on a question. If you are blocked, make the first line of `{report}` `BLOCKED: <the question, one line>`, SendMessage that same line to `{lead}`, then stop. A decision you can make conservatively, make it, and record it in the report under `DECIDED:`. A design choice whose wrong answer means rework (an interface or data shape, an ordering, locking or clock rule, behaviour other code relies on) is not conservative: ask it this way, since the lead answers in a few lines.
7. The last line of the report is `DONE`; a brief may instead require `DONE` followed by exactly one `AC_DONE:` verdict line (or it starts with `BLOCKED:` as above), then `touch {done}` as your very last act. Waiters watch `{done}`, not the report, so a half-written file is never read.
8. Never change anything outside the folders your brief names, and that includes shared tool state: Gradle's caches (`~/.gradle`, `~/.cache/gradle`), `~/.m2`, npm/pip/uv caches, SDKs and JDKs. A build that only works after you patch a cache (for example stripping jar signatures) is a finding to report under `DECIDED:` or `BLOCKED:`, not a fix. Every other build on the machine shares those caches.
9. In a worktree-isolated sub-agent (cwd under `.claude/worktrees/`), Claude Code's isolation guard refuses Bash commands it can't verify: loops, `cd … && git …` chains, pipes into decoders, heredocs that mention git, subshells with quoted globs. Run single plain commands, put anything compound in a script under your own worktree or folder (rule 28; never the shared session scratchpad) and run that script, and edit files with the Edit tool. If plain `git` is refused, call `/opt/homebrew/bin/git` directly.
10. Never run one foreground command for more than about 30 minutes: a client (historical OpenCode, 2026-10-13; OpenCode is archive-only under Pi-only) interrupted a 3,626 s one and that cancelled the whole turn, so the slice never wrote its report. Start long work with its output going to a file (`sh -c 'cmd > out.log 2>&1; echo rc=$? >> out.log'` run with the Bash tool's `run_in_background: true` parameter; a shell `&` is denied by the Bash gate since 2026-11-15, docs/bash-habits-gate.md; set that call's `timeout` to the run's need, at most 7200000 = 2 h, because the default 30 min stops the job; a longer job goes to CI (`~/CLAUDE.md` item 37), a `bin/ade-sched` one-shot or a Paseo terminal) and poll the file in foreground calls of under 10 minutes each (`bin/wait-file`, rule 13). A TUI without `run_in_background` (Codex, Pi, ...; the gate covers Claude Code only) keeps `nohup sh -c 'cmd > out.log 2>&1; echo rc=$? >> out.log' &`, or its own background exec (a yielded Codex cell, rule 13).
11. On this Mac, `sed` is BSD sed: use `gsed` (and `ggrep`, `gawk`, `gdate`) in every command you run, never bare `sed`, not even a `sed -i.bak` you expect to be harmless (2026-10-17: two slices in a row slipped). Remote Linux hosts keep plain `sed`; a nix/CI image may have none, so use a shell loop there.
12. Wrap every network command (`git clone`/`fetch`/`push`, `npm`/`pnpm install`, `curl`) in `timeout 600` or less, and clone a repo you do not already have shallow and blobless (`git clone --filter=blob:none --depth 1 --single-branch --branch <b> <url>`): a stalled transfer sits at 0% CPU with no error, so without a timeout the slice hangs silently (2026-10-17: two full clones of a large repo stalled for 30+ minutes). With an explicit repository argument, `gh repo fork OWNER/REPO --clone=false` does not accept `--remote`; that flag is only for the implicit current-repository form. Check argument combinations before a mutating command. Native launches use `paseo run` with `--cwd` / `--new-workspace` and a brief that already names `{report}` / `{done}`; do not invent dispatch flags. Serialize mutations of the same remote branch: a PR merge and another worktree’s push to that branch must not run concurrently.
13. Wait on a file only with `~/src/djbclark-ade/bin/wait-file [--timeout S] [--match '^rc='] /ABSOLUTE/PATH`, never a hand-rolled `until grep ...; do sleep` loop: it refuses (exit 2) an empty, relative or root-level path and a missing directory, and stops at its timeout (exit 124). Use poll or yield intervals of 30–60 seconds instead of rapid one-second polling; this does not shorten a task’s overall wait deadline. A yielded Codex executor cell is resumed with its `wait` tool (for example `yield_time_ms: 50000`), not by relaunching the command. `paseo wait ID --json` reads `idle` when the agent's turn has ended. A returned `session_id` or running cell is still in progress: resume it until completion and a successful exit before reading its downloads, artifacts or other dependent outputs. An existing partial file is not completion proof. Write paths as literals, and never `export` in a list you end with a background `&` (Codex/Pi; Claude's gate denies the `&`): the export happens in the background subshell, so the variable is empty afterwards (2026-10-17: waiters sat on `/install2.log` for 14 minutes and on `/install3.log` for 15, after the work had already ended).
14. Peer messages use `paseo send --json --no-wait <id> --prompt "…"` (or a trailing message string); ask for `ack <your id>` and prove delivery per AGENTS.md order 10. Address a lead by its current id (its latest takeover message, the succession ledger followed from the last id you knew (never its newest file), or the last `LEAD <id> took over` line of a run log it named) and send only after `paseo agent inspect <id> --json` reads `Archived: false`: a message un-archives an ex-lead (2026-11-14, docs/orchestration-practices.md 5a item 7). The `session-finder/relay.py` shim was deleted 2026-11-14. Direct UI input is for verified native commands and selectors. Verify a slash command in the installed client before submitting it: an unknown slash command can become a paid model prompt. Read the current visible screen after each UI change. Key APIs take supported key names or single characters; use the text API for selector search text, and check the app's own shortcuts before using an editing chord. Messages from the lead may arrive while you work. Between steps (after each commit, before each long command, and before you write the final report), read `{inbox}` if it exists. For every `## MSG N` you have not answered, act on it, and append `REPLY N: <one line>` to `{replies}`. A message overrides the brief where they conflict.
15. Lifecycle actions (`/new`, `/clear`, `/reset`, `/compact`, `/quit`, `/exit`, `paseo agent archive`, `paseo agent update --name`, and a handoff's Steps 8 and 9) run only in the operator's top-level session, never in a sub-agent or a dispatched slice: they inherit the parent's agent id and would clear, rename or archive the PARENT's session (found 2026-10-20). If a skill you run ends with one, treat that step as document-only, say so in the report, and let the lead decide.
16. Run tests and builds only through `~/ops/site-private/bin/bgrun` (full path); tiny smoke scripts and checks of documentation examples are tests too. Record the CI decision for the test's exact working Git root; a nested fixture repository needs its own decision, not its parent's. Use the documented `~/src/djbclark-ade/bin/load-watch ci decide` precheck (a review slice never records a `local` or `pending` decision, since both open the sudo-ask dialog: rule 29) (full path always works: bare `load-watch` is on PATH only after `ade-update` has linked it into `~/.local/bin` (step 3d, PR 860) and that directory is on PATH; it is not in `~/ops/site-private-djbclark/bin`); never run bare `load-governor`, which starts its daemon. Use **one pytest at a time**, never several trees in parallel and never a bare `pytest`/`uv run ... pytest`; the command is `bgrun bin/pytest ARGS` (CI's dependencies, 2026-10-28) (2026-10-23: one adversary round started ~10 parallel test trees outside `bg`, load 30 on 8 cores for five minutes, and the load watcher's memory gate never saw them). Mutation checks run one mutant after another, each under `timeout`, with `-k` of the new tests only. Whether CI can run it instead: `~/src/djbclark-ade/bin/load-watch ci decide`.
17. Before binding a local TCP test or web-client port on the Mac, claim it in `site-djbclark/registry/ports.yml` through the lead; an ephemeral test still counts. Prefer an owned private Unix socket when it fits. Never start on an unclaimed port and register it afterwards. Report every temporary server, its saved PID, and teardown result.
18. Never put Python source containing backticks or dollar substitutions inside a shell double-quoted `-c` argument; use a quoted heredoc or a script file. Bound tool output before printing it: save large JSON and transcripts privately, then emit only required fields or excerpts. Print one parsed structured result, not both it and a duplicate content block. A truncated output can hide a running session or write acknowledgement; recover the existing result before retrying. For auth-bearing configuration, extract only known non-secret fields or booleans before printing; never print whole lines containing credential flags, key prefixes, or a regex-redacted raw file. Treat JSON escaping and quoted argv as reasons to avoid raw-line redaction. A failed CLI may put its JSON error on stderr; check the exit status and both output channels before parsing stdout as JSON. In Python, use `subprocess.run(..., capture_output=True, text=True, check=True)` before `json.loads(r.stdout)`, or explicitly branch on `r.returncode` and retain stderr; never parse an unchecked `gh` response. Always retain the command result envelope, including session_id and exit_code, even when printing only an output excerpt. Before a batch, measure the combined character count in code and keep the printed payload below 12,000 characters (or a lower explicit cap); save the full output to a private file. Read one relevant document span at a time instead of several whole files. Before a batch, budget the sum of its outputs against the outer tool cap; extract fields or bounded line spans before printing. Do not print whole skills, quota JSON, or overlapping context windows. A smaller max_output_tokens truncates rather than summarizes; size it for the already-bounded result. Example for `graft`: capture it with `r = subprocess.run(argv, capture_output=True, text=True)` and write `r.stdout` to a private file before printing anything; never pipe it through `head` or `tail`. Then print `r.returncode`, the `tokens saved` banner line (relay it as the savings total) and only the requested source spans or fields, with their combined characters measured and cut to the 12,000 cap (or the lower outer cap) first. If graft says it fell back to a parent or another repository, discard its answer and build the graph in the intended workspace before continuing discovery.

19. Batch independent reads only. Routing, approval, ownership and mutation decisions depend on their returned evidence: read the fresh result first, then dispatch or mutate in a later tool call. Never resume a router and launch its dependent worker in the same batch.

20. Never block on a job longer than about 2 minutes unless your next step depends on its result. If something else can be done meanwhile, do it. If nothing can, write the status line to the report (what is running, where its log is, what to check next) and end the turn with it, and let the result wake you or the lead (2026-11-02: an agent sat 10+ minutes in a blocking wait with nothing depending on it, and the operator had to interrupt). A blocking wait also makes you deaf as well as silent: an agent that never goes idle cannot receive a peer message (`paseo send` to a busy non-steerable target reports no later delivery), so the lead's messages sat unread for hours; ending the turn with a status line is what lets them reach you. Never wait on CI (`gh pr checks --watch`, `gh run watch`): report "CI running", with the run URL, in the report and stop; the lead reads CI. Get that URL (or tell the lead where to look) with `gh run list --branch BRANCH` or `gh run list --commit <FULL 40-character SHA>`, never a short SHA: gh matches only the full SHA, so `gh run list --commit 5a2228d` prints `[]` with exit 0 and the poll never finds the run (2026-11-14, tendcf; `bin/completion-notice` expands such a short SHA with `git rev-parse` or refuses it). Since 2026-11-14 the Bash gate (`claude/hooks/bash_habits_gate.py`) denies `gh run watch` and `gh pr checks --watch` unless the command carries `--interval`/`-i` of 60 or more: one shared token has a 5000/h API quota (REST and GraphQL are counted separately), and four default-3 s watchers emptied it for an hour (10:22Z to 11:22Z). The 60 s exemption is for the lead's single CI wait; a worker still never waits on CI (this rule). Allowed instead: "CI running" plus the run URL and end the turn; a one-shot `gh run view RUN --json status,conclusion`; or a background loop that sleeps 60 s or more between one-shot checks.
21. In a fix-and-review loop (fix, push, review, fix), print or append one progress line per round to the report: the head sha and the finding count, for example `round 3: head 1a2b3c4, 2 findings (1 fixed)`. A long serial loop with no output looks like a hang to the operator. A reply to a peer that cannot be delivered because the target waits on a question or permission card is the operator's to unblock: check `paseo agent inspect` / `paseo permit ls`, record in the report that the message was not delivered and that the card is the operator's to clear, then move on; re-send once the card is gone, never wait for it.
22. **Push on completion (2026-11-09, updated 2026-11-13).** **If `{lead}` is `main` or `team-lead` you are an Agent-tool sub-agent: skip this rule.** The Agent tool returns your final message to the lead (`team-lead`, an agent-team teammate: SendMessage the `done:` line to it instead), `main` is a SendMessage name, not a Paseo agent id, and `completion-notice --requester main` sends nothing (`paseo send` would fail with "Agent not found: main"; 2026-11-13). The rest of this rule is for a `paseo run` slice, where `{lead}` is the requester's Paseo agent id. After `{report}` ends in `DONE` (or `BLOCKED: …` / `NO-REPORT: …`) and you have touched `{done}`, tell your requester once so it does not poll: `bin/completion-notice --send --requester ID --title TITLE (--pr URL | --status STATUS) [--report PATH]` (or `paseo send --json --no-wait -- {lead} "<message>"`). The message is exactly two lines — `done: <title>, <PR URL>` when a PR exists, or `done: <title>, <status>` / `done: <title>, <status>, <report>` otherwise, then `Please reply: ack <your agent id> <msg-id>` — and `{lead}` is the requester's Paseo agent id (the footer placeholder is that id when the brief sets it; otherwise the brief names the requester id). Right after sending, end your turn immediately so the session transitions to idle without streaming into turn replacement. Delivery is proven via dual routes (operator ruling 2026-11-12): (a) requester sends prompt `ack <your id> <msg-id>` only after verifying worker is idle (`paseo agent inspect`); (b) requester atomically writes `{done}.ack` on disk. Check ack with `bin/completion-notice --check-ack {done}`. Do not invent an APPROVE marker.
23. Launch apps or URLs only with `~/src/djbclark-ade/bin/open-clean` (same arguments as `open`), never bare `open`: macOS `open` hands your whole environment to the app it starts, so the app, and every shell later opened from it, inherits your session variables (2026-11-02: an agent's `open -a Quicksilver` left `CLAUDE_CODE_CHILD_SESSION` and `CLAUDE_CODE_SESSION_ID` in Ghostty and its shells, which lost their Claude transcripts and could be taken for the agent by relay). The Bash gate denies a bare `open`.
24. **Web search first and last (operator, 2026-11-13; queue Carried 34, now shipped).** Where prior art, a spec, an API or library doc, an upstream issue or a known bug could change the answer, search **before** you design, build or fix, and again **before** you report done. Tools, in order: the shared `mcp__firecrawl__*` (`firecrawl_search`, then `firecrawl_scrape` on a hit; never the paid `mcp__claude_ai_Firecrawl__*`), Context7 (`resolve-library-id`, `query-docs`) for library docs, `WebFetch` as the fallback (`~/CLAUDE.md` item 7). The brief carries a **`Prior art / docs checked:`** line (what you searched, with which tool, and what you found or `none`); copy it into your report and your PR body. Purely mechanical edits (renames, date bumps, typo fixes) write `Prior art / docs checked: exempt: mechanical`. Your report carries a **`Closing search:`** field **above the final `DONE` line** (rule 7 still governs the last line): the search run LAST against what you built (current docs, changed APIs, new upstream fixes, prices and model ids; e.g. the Fable 5.2 price copied unverified from 5.1, #627), with what it found or `none`. **Exempt** (state `exempt: <reason>` in the line and the field): mechanical edits, and slices no search could change (read-only status probes, reviews of a given diff). A report without the field, from a non-exempt slice, is unfinished (class 1).
25. Before committing or pushing a `changelog.d` fragment whose bullets already carry a real number, run `python3 bin/changelog-fold --repo . --check` and stop on a non-zero exit; fix the fragment first (every section needs a `###` heading, and every bullet a trailing `(#N)`). The PR number does not exist before the PR does, so (2026-11-21) until then end each bullet with the literal placeholder `(#PR)`: `changelog-fold --check` rejects it on purpose, so the check passes only after the number is filled, and your pre-push check is the heading and structure, not the number. Commit and push the branch with the placeholder, then open the PR with `bin/ade-pr-open --title ... --body-file ...` (the arguments of `gh pr create`; it runs `gh` through the adversary-marker shim and refuses `-R/--repo`) instead of bare `gh pr create`: it opens the PR, verifies the number with `gh pr view` (head branch and origin repo), replaces `(#PR)` with `(#N)` in the branch's own fragment, re-runs the check, and commits and pushes that file. `bin/ade-pr-open --existing N` repairs a PR whose fill failed (exit 4), including a fill commit that is still local. A fragment pushed with `(#PR)` still fails CI, which is the point: a forgotten fill stays visible. Mirrors the changelog-fragment paragraph of `skills/fan-out/SKILL.md` (2026-11-13: a worker pushed a fragment with no `###` heading and #637 CI went red; 2026-11-21: ten agent PRs in three days went red because the bullet had no `(#N)` before the PR existed).
27. **A read-only review never refills the graph (2026-11-19).** `graft ask` refreshes the freshness of `graft/` by default, which rewrites gitignored files even in a worktree you were told not to touch: three independent reviewers in a row hit this in briefs that said "do not run graft", because the repo's own `AGENTS.md` instructs graft use and the harness outranks the brief. So do not forbid graft in a read-only brief; require the non-writing form instead: `graft ask "…" --source --no-refresh` (and never `graft build`). If you must report a write you could not avoid, say so and note that `graft/` is gitignored, so a "tracked status clean" claim still holds while ignored state churned.

26. **Budget bulk GitHub API use (2026-11-14).** All agents share one GitHub token with a 5000/h API quota (REST and GraphQL are counted separately; it hit 0 for an hour on 2026-11-14: four `gh run watch` at 3 s, plus a lead's inventory script that fanned thousands of `gh api` calls over 6 threads with no check). A script that makes more than ~200 GitHub API calls first reads `gh api rate_limit` (`--jq .resources.core` for REST calls, `--jq .resources.graphql` for GraphQL, which `gh pr checks` and batched queries use), paces itself (a few concurrent calls at most; never `xargs -P`/thread fan-out in the hundreds) and stops at `remaining < 500`; prefer one GraphQL query that batches many objects over one REST call each. The Bash gate warns on `xargs -P`/`parallel` around `gh` calls. Check the quota before a gh-heavy step, and never use a watcher to wait (rule 20).

28. **Scratch files live in your own worktree or folder, never a shared scratchpad (2026-11-21).** Mutants, logs and probe output go under the worktree or folder your brief names (a gitignored or untracked subdirectory there), never a session scratchpad another slice can also be given: two adversaries reviewing different PRs both wrote `scratchpad/mut/out.log`, and one review's mutation results could no longer be trusted.

29. **A review slice never asks for an approval (2026-11-21).** A read-only review (an adversary or a delta check) never runs `load-watch ci decide DIR local …`, `bgrun approve-local` or any other command that asks the operator to approve something: each opens a real `sudo-ask` dialog on the operator's screen, and a timed-out one is logged as a denial in `~/.local/state/bg/approvals.log` (two reviews did this on 2026-11-21). If a local test would need an approval, run only what needs none, rely on the PR's CI results for the rest, and say so in the report. A build slice that must validate locally before a PR (`~/CLAUDE.md` item 37) still records its decision under rule 16.
